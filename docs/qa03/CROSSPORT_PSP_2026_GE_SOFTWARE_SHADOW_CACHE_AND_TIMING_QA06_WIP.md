## Most valuable NEW path: use PPSSPP's newly PSP-measured GE software renderer as a visual oracle

First-party PPSSPP engineering write-up dated **2026-10-02**: [Cracking the PSP GPU's transform and raster](https://www.ppsspp.org/news/ge-bit-exact/) and updated [raster pipeline](https://www.ppsspp.org/docs/psp-hardware/gpu/raster-pipeline/), [GE overview](https://www.ppsspp.org/docs/psp-hardware/gpu/ge-overview/). Author reports **~174 real-hardware microprobes and 125/132 PSP frame replays pixel-for-pixel identical** with current PPSSPP **software renderer**, with 29/30 frame-test exact matches; important *not* 100% and *not* evidence of native P4P fidelity.

Read exact from first-party documentation:
- **PSP GE pixel coordinates** 12.4 subpixel fixed point, top-left triangle rule, depth and fog interpolated by screen-plane fixed-point arithmetic; differs from host Vulkan/OpenGL/Direct3D floating-point rendering. In UI-A 48-segment **triangular fan** comparison, 0.5px boundary and alpha/scissor behavior should be assessed at true native **480×272** under software renderer before treating a hardware backend's antialiasing/scaling as a port bug. Source: [PSP raster pipeline](https://www.ppsspp.org/docs/psp-hardware/gpu/raster-pipeline/).
- **Scissor is the actual raster bound, not viewport**; triangles reaching huge offscreen coordinates are culled by finite guard band. For Junes RTT, fullscreen clear, All-Out panels, sky triangles and dungeon black-line leaks, log **actual scissor, framebuffer stride, format and depth** rather than assuming perspective viewport automatically clips. [GE overview](https://www.ppsspp.org/docs/psp-hardware/gpu/ge-overview/).
- **Color alpha equals stencil on PSP color formats** and there is **only 16-bit depth**; direct cross-compare software **color/depth/stencil** output for Apsaras/Zio, Junes shadow reader/writer, dark dungeon lines, translucent menus and TV/cutin masks. A mismatch visible in *software and PSP Go* but not host hardware backend strongly directs work to GE state/texture/VRAM; a mismatch visible *only on D3D/Vulkan* may be emulator hardware-backend behavior. However PPSSPP software has remaining known self-texturing/lazy texture/depth alias discrepancies, and neither emulator backend measures real Go frame time.
- **Crucial emerging emulator testing tool:** official [PPSSPP WebSocket Debugger](https://github.com/hrydgard/ppsspp/blob/master/docs/WebSocketDebugger.md) currently catalogs `gpu.record.dump`, `gpu.displaylist.disasm`, `gpu.buffer.screenshot/renderColor/renderDepth/renderStencil`, `gpu.stats.get`, `hle.thread.list`, `hle.semaphore.list`, `hle.backtrace`, log and input. The external automation host (not the PSP game loop) can trigger a **small evidence-capped dump only upon suspected failure**. Need bind API to an actually installed version with a handshake before assuming event availability; snapshots may contain copyrighted images/private scene content, never upload to public GitHub.

**Recommended triage matrix, not an observed fix:**

| P4P symptom | Repro PPSSPP hardware backend | Repro PPSSPP software GE backend | Repro PSP Go | Next decision |
|---|---|---|---|---|
| Black dungeon lines / Junes shadow / alpha cut | Yes | No | No/unknown | Emulator hardware backend may be responsible; record both settings, do not patch P4P prematurely |
| Same artifact at true 1× native in both emulators | Yes | Yes | unknown | Port or shared emulator issue plausible; inspect GE display-list state + source owner, then hardware |
| Software GE matches physical Go; Vulkan/D3D differs | Yes/other | Matches Go | Yes (matches software) | Prefer software Go visual oracle, investigate emulator hardware path; no global P4P geometry change |
| Software GE differs, hardware backend and Go match | Matches Go | differs | Yes (matches hardware backend) | Known software GE limitations such as self-texturing; don't treat software as universally authoritative |
| Only Go has an issue | No | No | Yes | Investigate memory cache coherency, GE async list lifetime, VRAM, firmware IO, thread timing and actual Go hardware; PPSSPP can't falsify hardware-only fault |
| All three share artifact | Yes | Yes | Yes | Focus on source shader-equivalent GE state, RTT, clipping, resource IDs, original Vanilla comparison; record linked PS2→PSP owner |

**Performance:** software renderer is **accuracy-focused and CPU-slow on PC**, not a PSP performance simulator. Use it for **pixel/stencil GE oracle** only. Benchmark with actual PSP Go T3, accepted display frame sequence, GE/CPU phases and 333MHz hardware settings.

## Cross-port details, verified original source and admissible P4P transfer

### XP-SM64 — JustKidding23/SM64-PSP native PSP port

Read actual [`PSP_BUILD.md`](https://github.com/JustKidding23/SM64-PSP/blob/master/PSP_BUILD.md), Git blob `48ada35a4e5f32b683db22a21a90a4d1f0f6a46e` as fetched in this session. Maintainer describes **lossless smaller textures**, a cache consuming spare VRAM and **6 MB main RAM**, **3× guard-band** before expensive software clipping and vblank pacing to avoid abrupt 30→20 FPS drop for a slightly late frame, tested there on PSP-3001 and GCC15.2. These are **author statements**, not P4P performance measurements. P4P already has mip swizzle/cache, its own `p4_guard_clip`/near plane/boxes, 64MB PSP Go resource constraints, fixed 30 game ticks and frameskip; **do NOT inject 6MB cache, a global clipping cutoff or different pacing blindly**. Actionable: record one **P4P scene's** texture miss/eviction, VRAM/heap headroom and guard inside/outside cost to determine if an analogous *local* improvement is useful; direct selftest for 1px non-power-of-two CLUT issue and texture raster invalidate.

### XP-MK64 — beckerd/psp_mk64_portable, real PSP tuning log

Read exact [`docs/fps60.md`](https://github.com/beckerd/psp_mk64_portable/blob/main/docs/fps60.md): project explains per-tick split-frame 60Hz mode with fallback to native 30Hz in heavy sections, game frame clock invariants, **GPU guard-band reject plus software near clipping**, **cached GE list writes in cache lines**, VFPU math, and main-memory logger because blocking Memory Stick writes are costly. It says three faults did not appear in PPSSPP and were only diagnosed on PSP. This reinforces our **no PPSSPP T2=>Go T3 promotion**, **cache-line/GE retirement** and **host-only recorder** priorities. **Never apply MK64's split-frame update hack** to Persona4's fixed 1/30 game clock, AI/script/animations and frameskip; even a 60FPS overlay output does not imply gameplay 60Hz parity. A low-risk transfer is the *diagnostic method*: log `game ticks`, `display accepted`, `GE work` separately and measure F009_004 p50/p95 on physical Go, with a freeze/low-VRAM control.

### XP-SSB64 — ItsNoHax/SSB64PSP display-list lowering

Read exact [`docs/rendering.md`](https://github.com/ItsNoHax/SSB64PSP/blob/main/docs/rendering.md) and [`docs/rendering/psp-lowering.md`](https://github.com/ItsNoHax/SSB64PSP/blob/main/docs/rendering/psp-lowering.md): **offline predecode and static mesh/GE preparation**, **preserve A-B-A order**, **material cache keys covering ALL texture-conversion inputs**, explicit distinction between **unknown** and **known set** GE state; guard-band clipping tested at specific geometry; defers more caching until real hardware profiling. P4P dynamic PS2 particle/RTT/Im3D flows are NOT all static N64 display lists, and P4P already has `call_replay`, `persist_try` and state cache. Actionable **audit cache invalidation and list source ownership** for stale Teddie portrait/mip or duplicate GE state; any use of static caching only for verified immutable geometry, collision/texture generation include raster IDs and palette generation, and preserve noncommutative alpha layering. Don't reorder transparent batches for CPU gains.

### XP-OOT-SHADOW — z2442/oot-PSP GPU silhouette tests

Read actual [`docs/psp-gpu-shadows.md`](https://github.com/z2442/oot-PSP/blob/main/docs/psp-gpu-shadows.md): replace CPU 64×64 shadow-pixel stamp loops with dedicated **EDRAM scratch RGBA mask**, GE draws stamps, transfer into separate texture cache entries, restore draw/scissor/stencil/depth state; host model compares **4,129 shadow masks** against original CPU output and checks state/texture/stride; PSP GE scheduling/precision not proven by that host suite. **Relevant to P4P Junes shadow** only as a *test architecture*, because original P4 Junes 128×128 RTT silhouette is already a different GPU feedback path and first suspected issue is **orthographic projection / clear/reader**. Adding another offscreen pass or 16KB+ scratch without proof would increase GE-list/VRAM risk. Instead build a small scene-specific RTT mask output comparator that checks **producer, clear target, input projection, transferred texture, consumer quad/UV/alpha and restored state**; only test on PSP after SEC-01 prewrite/list lifetime safety.

### XP-READOUT — PPSSPP hardware experiment method

First-party engineering lesson in [2026 hardware research](https://www.ppsspp.org/news/ge-bit-exact/): write *one small diagnostic display list that makes an unknown parameter visible* rather than blindly changing the entire production renderer; compare to actual PSP readback; guard readback size and do not send two simultaneous probes as hardware can hang. In P4P with a 64K-word list and dangerous cached-stall path this means **not** instrumenting long REND scenes directly with huge dumps; use host GE record and controlled PPSSPP first, PSPLink dev profile only with user approval and a stable GE preflight, no memory/bank retirement violation.
