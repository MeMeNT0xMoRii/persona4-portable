## REND-05 — new cross-pass hazard: perf06 RTT shares **main screen depth** (T1) even when color is redirected

Pinned [`port/rwsky.c` L1194–1216](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1194-L1216) explicitly documents: camera texture is drawn in own VRAM color rectangle, but it **shares the screen depth buffer**; its clear/draw overwrites the **upper-left** of the main scene's depth. RTT choices: `p4_rtt=1`, 4 slots, memory budget limited to the end of 2MiB eDRAM, fallback half-resolution. Exact [`rtt_bind_target` L1285–1307](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1285-L1307) switches `sceGuDrawBufferList`, viewport/scissor/texture states, **not `sceGuDepthBuffer`**. [`func_003f6a10` L1338–1372](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1338-L1372) invokes RTT selection as each camera begins. [`func_003f7490` L1403–1430](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1403-L1430) uses `sceGuClearDepth(0)` and `clear_striped` using **current** `target_w/target_h`. This is in addition to already mapped wrong-target pre-clear (the requested camera's raster is not necessarily bound when clear happens), missing parallel camera and nonindexed shadow Im3D.

**Conditional artifact mechanism (T0):** If a small offscreen camera clears or draws depth **after** main-world depth has been populated, it overwrites a top-left screen-space depth rectangle. Subsequent screen geometry can then fail its depth test there, even if the color target was restored. Alternatively, the game may order RTT early, in which case normal full-screen clear restores depth and no such corruption occurs. This **does not prove** original dungeon black lines, missing Junes shadow, white orbs, Teddie portrait or blue corners arose here. Repro needs temporal camera+target+depth-state trace; candidate **screen-space rectangular errors near (0,0)** are stronger than arbitrary diagonal/world-locked lines.

**Safe first test (debug only, after GE writer safety):** for Junes F009_004, Dojima, Castle, Apsaras/Zio capture sequence per *actually displayed frame*: `camera ptr`, camera+0x60 raster ID, type/size, selected RTT slot/VRAM offset+scale, **main vs RTT begin/clear/end order**, depth write/test and depth clear dimensions, GE list words, first main geometry after RTT. Compare screenshot + depth-buffer history under matched camera movement. Confirm via frame-local absence/presence of a rectangular screen-coordinate artifact, not camera independent intuition. **Potential isolated solutions to benchmark**, not prescriptions: order RTT early before main depth is built when equivalent to original render order; camera-scoped depth isolation only if GE memory/headroom permits; or explicit depth restore if possible. Never disable RTT globally, clear all screen depth midframe or allocate an unbudgeted second 512×272 depth buffer.

## PROF-03 — outside-the-box: use *existing* P4P .ppdmp capture as foundation for **per-pass GE cost / command-accounting**

Our perf06 already contains [`port/ge_dump.h` L1–16](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/ge_dump.h#L1-L16), adapted MIT from dreikk91 b339. In **separate serial** `P4_GE_DUMP` build `L+R+SQUARE` arms next drawn frame to write **PPSSPP GE dump format v6 `ge_NNNN.ppdmp`** (textures, vertices and executed CALL/RET/JUMP included). It is **not missing**. [`rwsky.c` L454–461](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L454-L461) forces `p4_pipeline=0` with `P4_GE_DUMP`, so its FPS and stalls are **not stock comparable**. The dump recorder reads some memory at end of frame; [ge_dump.h L1–16](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/ge_dump.h#L1-L16) explicitly warns that CPU-updated textures/vertices may show final state, not at-draw state. `.ppdmp` contains copied copyrighted source textures/geometry; **keep private**; GitHub only hashes/derived numeric counters.

**External source-verified native-PSP technique:** OpenUG2's [`psp-viewer/probe.h` L1–25](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/probe.h#L1-L25) divides frames into **CPU-phase timestamps, live GE signal arrival per pass, solo GE replays and parsed command-list work** (draws, vertices, vertex bytes, textures/CLUT transfers and matrix loads). [`probe.c` L90–155](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/probe.c#L90-L155) parses finished display list with bounded operations, follows BASE+JUMP, CALL/RET, tracks VTYPE/PRIM/TEX and screen box where vertex format permits. [`probe.c` L31–90](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/probe.c#L31-L90) uses GE signals per render pass, with a *replay alone* diagnostic that must not be conflated with stock pipelined frame pacing. In external game's own source, **per-draw signals perturb timings and callbacks have latency**, so broad A/B uses capped markers rather than instrumenting every draw on a player's PSP.

**Practical P4P adaptation order:** 
1. **First no game-code change:** inspect existing private perf06 `.ppdmp`/PPSSPP lab GPU captures if available and parse *offline* into a **stable CSV manifest** keyed by SHA256 of paired EBOOT/data/strings, exact scene/game frame, and source/control commit. Use decoder matching format v6 (not naive `uint32_t[]` on file bytes), count GE commands per pass/material/texture/CLUT load, draw primitive+vertex/index count, RTT, GE CALL sublist and alpha writers; bound traversals and nested CALL depth against malicious/corrupt dumps.
2. For actual **real PSP Go CPU vs GE**, use a **separate low-overhead phase-marker** diagnostic only where missing (pipelined), not a serial `.ppdmp` FPS comparison. Read [`port/frame_timing.h` L27–74](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/frame_timing.h#L27-L74) existing p50/p95/32 frame windows and writer budget separately; `hwpeak listB` is the **slowest wall frame** list length, not maximum list occupancy.
3. Decompose Junes vs School vs Shopping North/South by **world sectors, opaque geometry, skinned models, UI/2D, RTT, alpha/VFX, GE wait, present**, and compare one feature switch A/B/A at same save/frame. The purpose is to distinguish **CPU command emission / cache stalls** vs **GE texture/fill** without sacrificing visuals.

**Second external diagnostic to consider only after SEC-01 safety:** [OpenUG2 `psp-viewer/gudraw.c` L100–178](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/gudraw.c#L100-L178) has a `GU_LIST_AUDIT` that snapshots command/cache lines the GE had been allowed to read and checks for **late CPU writes** to those same lines, attributing first changed byte to `sceGuGetMemory` caller. This is a specific strategy to investigate **intermittent flicker, stale geometry and one-frame corruption** that PPSSPP may not reproduce because it has no physical CPU data cache. Our [`rwsky.c` L675–711](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L675-L711) likewise writes cached lists and flushes on wrapped stall updates, so the underlying lifetime/visibility question is real. **But external probe is NOT a buffer-overflow guard**, and its audit memory can be large; don't copy code unreviewed or add it to production perf07.

## PERF-04 — measured *external* GE-stall batching and compiler layout, not a free P4P FPS toggle

[OpenUG2 `psp-viewer/gudraw.c` L1–55](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/gudraw.c#L1-L55) uses batched `sceGeListUpdateStallAddr` calls every 32 draws and 16 CALLs; external author states roughly **8 µs per draw kernel call, ~8 ms of its street CPU command time on its own PSP-3000**, not this P4P game. P4P pinned [rwsky.c L1868–1869](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1868-L1869) **already batches 8 draws and has specialized direct GE** with stall update deferrals. A/B of 8 vs 16/32 could save host-side CPU but risk **GE starvation, P0 list-cap pressure and delayed cache writeback**; require CPU stall vs GE wait + visual no-corruption validation. Do not blindly adopt external timing or disable stalls entirely.

**More speculative future option:** OpenUG2 [`psp-viewer/Makefile` L77–115](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/Makefile#L77-L115) reports **LTO alone +1.5% CPU cycles, PGO+LTO −6.9%** in its own street test. Its [`hot.ld` L1–25](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/hot.ld#L1-L25) rearranges hot functions/library segments to reduce PSP instruction-cache conflict misses. P4P already notes a past **61% memory-stall CPU cycles** measurement (b240 comment; not current Go) and [`tools/psp_hw_debug.py` L60–65](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/tools/psp_hw_debug.py#L60-L65) permits `P4_PORT_OPT=-Os` as an old instruction-cache experiment. **PGO/LTO and linker hot-layout are T0 for P4P** and may invalidate exact reassembled addresses/relocation or fixed `.p4image`; try *port-only* selective transformations in a distinct diagnostic branch after toolchain layout proof. Do not treat external percentages as expected P4P FPS.

## BOT-02 — development-only remote rescue and log-polling strategy (external source T1, P4P implementation T0)

External native [OpenUG2 `psp-viewer/probe.c` L210–259](https://github.com/jussimir-labs/OpenUG2-PSP/blob/main/psp-viewer/probe.c#L210-L259) implements a separate **priority 0x30, 4KiB** PSP worker `HostCmd`. It checks for `hostcmd.txt` in the **PSPLink `host0:/` mount rather than polling the Memory Stick from game update/render**. The source comment explains an earlier card-directory search had introduced a few milliseconds of game-frame delay and blocked loading. It supports dev-only `suspend`, graceful `exit`, a bounded 5s emergency exit, and shuts down on `RELEASE`. Its actual `host_cmd` is a configurable path string, and the static read interval is ~1s (`sceKernelDelayThread(100000)` × `host_every=10`), despite a comment claiming two seconds. Treat source implementation/timing, not the stale comment, as authority.

**P4P application candidate:** separate host-side PPSSPP WebSocket/PSPLink watchdog from the game frame and `p4io` semaphore; send heartbeat/state snapshots only via bounded developer mode, allow 10s host stop/reset, never overwrite saves or poll `ms0:/`/internal `ef0:/` every frame. On a retail Go without PSPLink, a device-local optional sanitized bug-report trigger should *write once* when requested, not continuously read storage. This is not current `tools/ppsspp_lab.ps1` capability and has not been implemented or hardware tested. The opt-in crash/rescue feature should not change normal audio streaming or performance.
