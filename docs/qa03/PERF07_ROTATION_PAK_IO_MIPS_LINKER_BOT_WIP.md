# QA03 — rotation: original package loading vs PSP synchronous file adapter; linker headroom; mip fidelity; long bot replay clock

**2026-11-19, source audit + synthetic host logic checks.** Gameplay/runtime baseline: `MeMeNT0xMoRii/persona4-portable@29b0fcfdec70222a4052099b67fb4a11e8d8aff4`; original PS2-US decomp pinned `Raikaru/Persona4-Decompilation@363eab8a966d60a9773b45f330f2344329ec4f0a`; documented PSP SDK snapshot `pspdev/pspsdk@09f02b88b9f3`. **No runtime game edit, build, PPSSPP, PSP Go, save or screenshot publication**. T1 static source verified, T0 symptom/caller execution unproven, synthetic host demonstration is NOT emulator T2.

## IO-01 — new cross-source loader mismatch requiring early diagnostics (P1 research, high potential if active)

**Original Vita/Golden is not the authority here; compare the PS2 USA source directly.**

- Current [`port/files.c` L147–201](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/files.c#L147-L201) implements `func_004c9010` (original ADXF read) with one **synchronous, semaphore-serialised `sceIoLseek` + `sceIoRead`** sequence. It copies `Handle.h->offset` into a **local `long long offset`**, increments *only that local value* during a potentially multi-part single call, and never writes the resulting offset back into `h->offset`. On completion sets `h->stat=3` immediately. This is **not an automatic defect for single full-file reads**.
- Original [`src/Kernel/sdkCdvd.c` `H_Cdvd_UpdateRequests` **FUN_00454640** L119–200](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Kernel/sdkCdvd.c#L119-L200) often requests **an entire archive in one `func_004c9010(handle, total_sectors, memory)`**. That one-shot use is compatible with the PSP implementation and must not be mislabelled corrupt.
- **New source mismatch is in the separate package loader** [`src/sdkPak2.c` `sdkPakUpdateDirectoryLoads` **FUN_00468A50** L52–95](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/sdkPak2.c#L52-L95). State 2 calls `func_004c9010(same_handle, 1, headerAddress)`, and state 3 (on READEND) calls it AGAIN with `sectorCount` for `directoryAddress` **without reopening/changing the handle**. The original [`src/cri/re4/adx_fs.c` `ADXF_ExecServer` L222–242](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/cri/re4/adx_fs.c#L222-L242) advances ADXF `ofst += rdsct` when a read completes, maintaining a sequential read cursor. The PSP replacement's handle offset does not move. **If this sdkPak2 request path is active in perf06, the directory read would return the header sector again instead of the next sector**. If this path is unused, it cannot explain current symptoms. Caller execution T0 until runtime trace.
- **Synthetic host logic check, not PSP execution:** Given a test archive with first 2 KiB = `H`, second 2 KiB = `D`, model of current `h->offset` retention outputs **H then H** for two consecutive one-sector calls; original sequential `ofst` semantics yields **H then D**. This is a direct logic consequence, not a tested game failure.
- Additionally [`sdkPakStartEntryLoad` **FUN_00468BF0** `src/sdkPak2.c` L106–145](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/sdkPak2.c#L106-L145) calls `func_004c8708(path,0,start_sector,count)` to open a **range** for an individual package entry. The full 210-line current `port/files.c` **does not define `func_004c8708`**. Original pinned `src/promoted/code1_004c.c` lists `FUN_004C8708` as an unported ASM function, whereas `tools/psp_link.py` excludes ordinary `src__cri__` objects and may reassemble or stub such unresolved calls. **Whether the perf06 executable has a valid native fallback is NOT confirmed**: must check generated `build/psp/missing.txt`, `reasm_cases.tsv`, ELF symbol at native/rebased address and actual PSP caller before declaring broken. Do not implement range-open or patch `h->offset` globally without caller/handle semantic proof.
- Original `H_Cdvd_UpdateRequests` **calls `sdkPakUpdateDirectoryLoads` each update**, but this proves only an update hook exists, **not that nonempty package requests actually execute**.
- **Perf question independent from misread:** current synchronous `sceIoRead` may block a retail update thread, and PSP I/O is shared behind `p4io` semaphore across several game loaders. An occasional load stall can appear as stutter, but there is no verified steady-state School/Junes slowdown due to storage. Profile I/O duration/count and waiter, I/O thread and scene ID before proposing asynchronous loader or prefetch.

**Safe next approved test:** Using private legally sourced assets only, first inspect generated ELF map and `missing.txt`; log bounded `sdkPakUpdateDirectoryLoads` active request state, `file path hash`, handle cursor, consecutive read counts, unique attempted range opens, file headers vs directory sector header, errno and load state; parallel collect synchronous `sceIoRead` wall duration/p95 in School/Central Shopping scene transitions and audio load. Test on PPSSPP and then Go. Do not dump raw game packages publicly. Use a reversible, adapter-local fix only after proving active execution and intended semantics. Regression: full-file H_Cdvd one-shot loads, shops, Velvet, field transitions, movie/audio, no duplicated package data, CPU/GE 20FPS floor unaffected.

## MEM-01 — static GE-list expansion has existing linker-position protection (corrects overly broad memory-collision risk)

- [`tools/psp_make_data.py` L17–21](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/tools/psp_make_data.py#L17-L21) pins **`PSP_IMAGE=0x0900DA00`**, retail data start `0x0052DA00` and translation `K`; comments say there is spare pre-image code space (not measured on current EBOOT).
- [`tools/psp_link.py` L194–224](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/tools/psp_link.py#L194-L224) emits a `.p4image (NOLOAD)` linker section after `.bss` with **fixed address** and uses `assert table['p4_image'] == PSP_IMAGE` before data construction/packaging. [`port/main.c` L18–40](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/main.c#L18-L40) reserves `P4_IMAGE_SIZE=0x40B000`. Thus a **normal clean build** whose growing code/BSS makes `.p4image` move is **expected to be detected at build/link time**, not silently accepted. The real headroom of that build and all other sections still need inspection: a fixed address assertion is not a general RAM/heap safety guarantee.
- **Correct P0 split:** (a) check static `.bss`/pre-image layout against fixed `p4_image` + clean-link assert, (b) check runtime **malloc/heap max contiguous and thread stacks** after main image + two 65,536-word GE lists + 1MiB on-demand GE ring + mesh cache, (c) check two **GPU banks' command-list overruns** at runtime; a build-time section alignment assertion does **NOT** protect a runtime `gu_list->current++` or variable `memcpy`. Optional `p4_memstat` consumes additional ~768KiB if enabled; preserve debug vs stock distinction.
- Increase to 128Kiword double lists only after individual and combined capacity checks. P4P [`port/main.c` L484–510](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/main.c#L484-L510) already logs `sceKernelTotalFreeMemSize`/`sceKernelMaxFreeMemSize` at boot (not list high-water). No new memory data measured here.

## VFX/TEX-01 — original PS2 4/8-bit and 16/32-bit raster mipmaps use direct point samples, not filtered source footprints

- Current [`port/rwsky.c` `mip_levels`/`mip_decimate` L1090–1132](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1090-L1132) chooses only **power-of-two** rasters of minimum **64×64** and creates each level from *level 0* by selecting texel `(x << level,y << level)`, including palette indices for **T4/T8**, not filtering RGBA/alpha. Swizzle stage [L1137–1180](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1137-L1180) also allocates separate temporary level buffer and can silently fallback to **level 0 only if memory tight**.
- Actual bind [`rwsky.c` L2713–2746](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L2713-L2746): indexed texels loaded via original palette, **`GU_LINEAR_MIPMAP_NEAREST`** if levels>1, linear otherwise, `GU_TEXTURE_AUTO` level selection. This may be appropriate for bandwidth, but **point decimation and hard mip-level switches** are *plausible* reasons for thin-texture shimmer/disappearing detail/edge aliasing in School/Shopping. Scene/material attribution and actual screenshots with same camera still T0; bad lighting/texture resolution/missing geometry may be separate problems. Do not claim a globally clearer result from one filter toggle.
- **Alternative with low runtime cost:** test an **offline-only, per-asset optional mip generator** that computes filtered footprints in original RGBA and quantizes to source T4/T8 palette using alpha-aware nearest palette entry; retain exact level 0, test chain quality/alpha coverage vs current point mips, allow scene-local opt-in. Be careful: downsampled alpha coverage and nearest-index quantization can change masks, and preserving Vanilla art is higher priority than smoothing every edge. Offline candidate also needs on-disc memory-format footprint and local builder generation/hashes, PSP swizzle/GE valid texture sizes/LOD. An alternative first test is a **per-material mip disable / LOD bias comparison**, not global mip removal: if GPU bandwidth rises too much, reject despite screenshot gain.
- Before writing code get **`mip_textures, mip_bytes, swizzled_textures, swizzled_bytes`** and list of material raster widths/depth/CLUT used by School, North/South Shopping and Junes. If not eligible for mips, mip quality cannot explain that individual model. Link P4 original RenderWare raster→native `bind_raster` and texture IDs; have an opacity/checkerboard negative control. Need present-FPS p50/p95 and p99, CE no seams, original PS2 texture comparisons. Current VFX alpha/RTT issues have different owners.

## BOT-01 — absolute replay time also wraps at 71.58 minutes; the pinned SDK offers a 64-bit clock

- Current [`port/pad.c` `route_apply` L80–95](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/pad.c#L80-L95) checks route timestamps against `unsigned now = sceKernelGetSystemTimeLow()/1000`, with no route-start normalization. `sceKernelGetSystemTimeLow` returns the **low 32 bits of a microsecond timer** per PSPSDK header [`src/user/pspthreadman.h` L1588–1595](https://github.com/pspdev/pspsdk/blob/09f02b88b9f3/src/user/pspthreadman.h#L1588-L1595). 2^32 µs ≈ **4294.967296 seconds = 71.5828 minutes** until low clock wrap. Since division by 1000 happens **after** wrap, an absolute route with a long play session can unexpectedly drop `now` back to ~0 and release held buttons / fail future events. No actual running story bot or observed emulator wrap yet.
- That **same pinned header** declares `SceInt64 sceKernelGetSystemTimeWide(void)` at L1588–1590. This is a source-proven 64-bit timebase option; whether linking/behavior is correct in the actual perf06 local SDK must be checked. The earlier [replay-origin mismatch](PPSSPP_ROUTE_TIMEBASE_DETERMINISM_BOT_WIP.md) is **a separate issue**: a 64-bit clock alone does **not** normalize recorded timestamps or make input state deterministic.
- **Synthetic arithmetic test** (Python host only; no PSP/PPSSPP): for first recorded input at `t=418.7s`, new route start at uptime 2.0s delays input **416.7s**, at 200s delays 218.7s, at 418s delays 0.7s, at 500s it fires immediately; `2**32/1e6=4294.97s`. Based strictly on source arithmetic. Earlier BOT-0 route support exists, but not a complete autonomously playing tester.
- **Safe test ladder:** version old absolute route v1 unchanged; new route v2 uses **64-bit elapsed microseconds from a named activation checkpoint** and explicit press/release, monotone event validation, expected game-state assertion, host/PPSSPP replay 3× across startup delays, then synthetic 72+ minute timeout/wrap scenario and later long Velvet/dungeon simulation. Handle suspend/resume and savestate deterministically; at full story length don't rely on 32-bit unsigned delta alone unless periodically accumulated. Never control user input or overwrite saves while doing private diagnosis.

## Scene mapping blocker: filenames erased from shipped index

- [`tools/psp_disc.py` L85–99](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/tools/psp_disc.py#L85-L99) collects original relative **file path, LBA, size** privately from game disc, then writes `p4files.idx` with only **(32-bit FNV-1a path hash, container/offset, size)** sorted by hash; [`port/files.c` L58–125](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/files.c#L58-L125) loads and hashes names for lookups, logs **only missing** paths by default. Thus `p4files.idx` on its own **cannot unambiguously tell us which hash is Central Shopping vs School**; the original textual names have been discarded. The concrete next step needs a **private per-build asset-name lookup before packing** and/or opt-in successful-open trace at field scene boundaries, then source/game room/camera IDs. Never infer Central Shopping's room ID from Shopping North and never publish the extracted game package itself.

**Rotation conclusion:** New P1 loader semantics discrepancy is more important to validate than optional cosmetics; P0 GE SDK+main-list protection unchanged, both never patched. Memory/address and texture hypotheses are clearer. Bot long-run timebase has an independent exact wrap limit and an SDK-provided 64-bit solution option. No T2/T3 test or new FPS in this research.
