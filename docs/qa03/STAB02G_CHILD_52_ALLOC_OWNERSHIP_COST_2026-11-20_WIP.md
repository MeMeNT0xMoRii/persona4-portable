## Allocation-failure semantics and record-bound follow-up

- Earlier STAB-02f highlighted a missing local check for `btlUnitCreate`'s returned child. **Refinement:** if the first `0xA70` allocation itself returned NULL, **`btlUnitCreate` dereferences it in its own L144 `memset` before it ever returns**. So instrument **at allocation entry/return and at inner placement/pool allocations**, not only the outer `btlUnitInitChild` return. If allocator traps or never returns on failure, that produces a different symptom; this is **not an observed null dereference**.
- [`btlUnitInitFromRecord` `FUN_0019EA60`, `btlUnit_inferred_0019e9f0.c` L167–260](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlUnit_inferred_0019e9f0.c#L167-L260) genus 2 takes **`childOffset=characterId*0x58`** at L222 and reads metadata from `iGpffffb3e0+childOffset` without a local child-record count/range check; the caller passes u16 ID. **The actual child-record resource extent and real script key domain remain unknown**; do not label a particular ID out-of-bounds without metadata length and real input.
- **Cleanup exists; no general leak claim:** [`btlUnitUnlinkAndFree FUN_0019D550`, L106–154](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlUnit_inferred_0019d550.c#L106-L154) recursively unlinks/frees child, placement and pool, and [`btlEffectFreeNodePool FUN_001D6C10`, L139–170](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlEffect_inferred_001d6a60.c#L139-L170) walks/frees all 48 nodes. [`btlUnitReleaseAllResources FUN_0019D4E0`, L102–124](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlUnit_inferred_0019d4e0.c#L102-L124) also releases child recursively, and [`btlUnitFreeRemovedUnits FUN_0019D670`](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlUnit_inferred_0019d670.c) uses that during battle teardown. These are **freed under expected lifecycle**; no leak demonstrated. Because `btlUnitReleaseAllResources` does not visibly zero the parent `childUnit` field, an incorrect repeated cleanup *could* leave stale ownership, but whether a parent can survive for re-use after that cleanup is **unproven**, not a confirmed double-free.
- Core nuance: **52 operations may affect frametime even if memory is never exhausted**, but counting them alone does not establish that they land in the *same frame*, that they are slow, or that the observed enemy-reinforcement event uses this path. The `btlUnitCreate` call is synchronous in its source, but scheduling/scene timing and allocator cost need T2/T3.
