# QA03 — PS2-faithful visual quality with PSP Go 20 FPS floor / 30 FPS target: source-backed engineering plan
2026-11-19, research only. Runtime baseline commit 29b0fcfdec70222a4052099b67fb4a11e8d8aff4 on dev/v0.27-perf06. No PSP Go or PPSSPP benchmarking in this pass; all performance numbers below are targets, prior-project historical measurements or external-project claims explicitly distinguished.

## Absolute goal and acceptance gate
- Short term: **20 FPS consistently in each scene**, implying up to 50 ms **present-to-present** wall budget, not just average internal game ticks. Stretch: stable ~30 FPS = 33.33 ms presented frame; no minimum guaranteed yet.
- Measure **native PSP Go 333 MHz**, 480×272, unmodified native render scale and user-approved clock profile. Record p50, p95, p99 for presented frame, CPU-side frame, accumulated GE wait, last GE tail and missed vblank; note RAM free/max contiguous, VRAM allocations, list high-water and texture upload rate. Avoid a single average FPS number or PPSSPP 'unlimited speed' as hardware proof.
- Establish a frozen 15–30 second replay route for every representative scene: Junes West **F009_004**, department store, school corridor, Central Shopping District North and South, Samegawa Riverbed, Dojima, Castle fog/dungeon, town map, title→intro→title, Persona fusion/Velvet and 1–4-party battle. Capture static camera and moving camera tests separately, morning/rain/night/fog where they differ. Analyze at least three repeats per change. **No reported measured new scene performance**.
- Preserve first-party Vanilla PS2 USA material/geometry priorities; Golden 16:9 geometry only. PS2 fidelity is correct camera projection, texture sampling/lighting/blend/depth, materials, detail and temporal stability — **not** 4× PCSX2 texture packs. More pixel density at 480×272 may be useless while consuming RAM and texel bandwidth.

## Lessons from other native PSP ports, with exact inspectable public source

**OpenUG2-PSP by Jussimir Pasold**: https://github.com/jussimir-labs/OpenUG2-PSP (current README release **v0.4.0 open beta**, November 2026; its KNOWN_ISSUES explicitly **does NOT claim global stable 30 FPS** or full original progression). The developer built a new PSP C/GU engine with offline conversion from user-supplied Xbox/PS2 NFSU2; this is **not a ready-to-transplant PS2 renderer/recompiler**, and 30 FPS in one observed drive is not a universal FPS guarantee.

Specific reusable concepts verified in current source:
1. **Precompute geometry bounds offline**: tools/n2cy_bounds.py L2–13, L56–86 appends per-batch s16 bounding boxes and triangle counts so the PSP loader does not scan every vertex at runtime; psp-viewer/world.c L78–85 stores bounds and prebuilt draw items. For P4P: only on static RenderWare mesh data after archive provenance+checksum validation, same program behavior with no lost meshes.
2. **Pre-record stable GE state/draw commands**: psp-viewer/world.c L81–85 stores segment command lists compiled at load. P4P could trial similar static-world batches with invalidation on texture/material/matrix changes, and preserve command-list memory bounds/CPU-GE sync.
3. **Offline select mipmaps / palette**: tools/convert_mips.py L2–19 and L42–80 creates swizzled CLUT8 mip levels with alpha-aware palette lookup to retain foliage coverage. P4P should first audit existing raster and mip support: improve corridor/road texture stability where needed, avoid costs of generating/re-uploading every mip each frame.
4. **Real conservative LOD/visibility and prioritized streaming**: psp-viewer/world.c L70–85 LOD, section gates, near/far batches; psp-viewer/stream_predict.h L1–17 bounded route prefetch. P4P may benefit from field-cell/sector streaming and prefetch before camera transitions **only if current memory/IO profiling proves a hitch**. Persona scenes are room-based, not racing open-world; do not blindly copy geographic streaming.
5. **Specific math/particle optimization**: psp-viewer/rain.c L38+ comments measured float conversion overhead and uses fixed-point for rain draw, records separate move/draw time at L283. P4P orbs/thunder/field particles could use similar verified hot-loop substitutions after comparing shape/visual trajectory; not a generic license to simplify effects.
6. **Telemetry and user QA**: source README current v0.4.0, KNOWN_ISSUES, docs/TESTING.md: build/data IDs, two memory profiles, versioned outputs, screenshot/FPS capture, L+R+SELECT saves a technical bug file; one issue per defect and no retail ISO in repo. P4P could add a user-initiated opt-in "capture last N state breadcrumbs" and log bundle, title build ID + hash, hardware model and safe save provenance.

**The Simpsons Hit & Run PSP** https://github.com/antoxa2584x/SHAR-PSP (psp-port): README confirms **front-end** on real PSP-2000, **gameplay not yet working**; tools/p3dopt README uses offline CLUT8 conversion (24MB→~7MB of frontend textures under its particular data) and geometry decimation for constrained memory. Good example of memory-led asset processing, not evidence a 50% triangle reduction is visually free or suitable for P4P. Never cite its gains as our measured results.

**PPSSPP author's hardware notes** https://www.ppsspp.org/docs/development/psp-internals/ge-performance/ : separate CPU/GE through dual lists, stripe clears (32px for RGBA8888; 64px for 16-bit), smaller s16/s8 vertices, minimal bone count, reusable GE state sublists, CLUT4/8 and swizzle. Existing P4P already implements several; compare exact paths before recommending redundant changes. This source warns indexed triangle lists can be slower than strips on GE, so any offline mesh remap must be A/B tested, not assumed.

## Scene-first image fidelity plan (avoid generic "ultra" preset)
- **School Corridor**: capture settled/moving camera, model/room sector list, material/texture names, edges vs intended PS2, floor/decal lines; classify GE fragment fill, number of visible rooms, skinned actors, texture shimmering, alpha and z. If large CPU task work dominates, prioritize guard/sector + task cache. If surface texture is blurry/missing, identify mip or raster state (not boost global 4× texture size).
- **Central Shopping District North/South**: investigate camera width, horizon/pop-in/backface/guard, texture alpha, culling and shop panel overlays separately; measure time of day/weather and distant geometry; guard against temporal flicker and excessive conservative-cull false negatives.
- **Junes West F009_004**: measure 128×128 RTT pass list, camera projection+clear, missing shadow Im3D, scene geometry, alpha throughput, GE waits and load time. Suspected wrong shadow has no verified 20FPS benefit.
- **Dungeons**: original FieldNoise is disabled in perf06; black lines arise from another active path. Test 16-bit depth, decal, world-space vs screen-space, guard or RTT before any extra full-screen fog passes.
- **Battle/Fusion**: correct local circles and 2D alpha only after P0 GE memory safety; track meshes, skinning, effect strip count and every framebuffer bank; avoid extra cost to restore optional glow if hardware can't hold frame budget.

## Codex/Work measurement order and stop conditions
1. Establish **baseline and full build provenance** from fixed EBOOT/manifest and original ISO hash privately; never compare different EBOOT builds as one data point; no game assets public.
2. P0 GE-list capacity and memory-headroom safety; original/minimal/complex save controls; stable HOME/save.
3. Repeat identical camera/route captures across high-cost scenarios (Junes, corridor, street, dungeon, title and fusion), log presented p50/p95/p99 and GE list words, CPU/GPU/IO/culling breakdown.
4. For every hypothesis make exactly **one** scene-local feature flag change, measure hardware, and preserve before/after PNG+logs private. If code fix creates crashes, new cull holes or new p95 regression, rollback. Benefits must preserve original PS2 appearance and other locations.
5. Only after 20FPS floor across sampled scenes consider 30FPS stabilization and additional high-fidelity features; never promise global 20/30 without complete playthrough/scene table.
