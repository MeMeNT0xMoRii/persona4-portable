## A. Source-verified effective flags, lifetime and hidden feedback coupling

- Frozen [`port/rwsky.c` L1202–1273](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1202-L1273) allocates at most **`RTT_SLOTS=4`** `RttSlot` structures. `rtt_find(r)` returns a previously allocated slot by Raster* identity. **`rtt_get` returns that prior slot immediately `if(s || !p4_rtt || ... ) return s;`**. Therefore turning **`p4_rtt=0` after an RTT slot has been created does NOT turn it off for that raster**: subsequent `rwSTANDARDCAMERABEGINUPDATE` [L1339–1370](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1339-L1370) still binds cached `rtt_get` slot. Frozen [`bind_raster_body` L2698–2711](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L2698-L2711) **also continues sampling that slot's VRAM image** without checking current `p4_rtt`. **A live debug variable toggle is not a valid RTT ON/OFF controlled comparison for existing scenes.** This is a source-proven diagnostic trap, not proof that user tested or toggled it.
- **`p4_rtt_scale` is used only inside the newly allocated `rtt_get` for-loop**, [L1258–1266](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1258-L1266). Once the Raster* has an existing slot, changing scale to 2/0/1 mid-scene does **not resize the slot**; A/B scale changes require a fresh known state or correct raster destruction/recreation. The `scale` field is stored in the slot; log **effective** slot scale/w/h/offset, not just user-requested scale.
- **`p4_rtt_scale=1`** first tries full-size allocations at **`RTT_FULL_BASE=0x154000`**, overlapping the VRAM location normally used by the full-resolution screen feedback copy `capture_feedback_vram`, while `p4_rtt_scale=0` uses only the tail `RTT_TAIL` and falls back to half-size. On a successful full-base placement, **`p4_feedback_half=0` is assigned** [L1260–1265](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1258-L1265) to avoid overlapping feedback capture. Current default `p4_feedback_half=1` [L2536–2542](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L2536-L2542) is VRAM copy; **0** selects full-screen capture into **1 MiB RAM buffer** via `capture_feedback()` [L2507–2534](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L2507-L2534) and [`bind_raster_body` L2655–2685](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L2655-L2685). Source comment says RAM feedback cost **~50 ms of GE on a past Dream fog scene**; **not a recent perf06 Junes measurement and not a measured effect of sticky state on this run**. GE may be memory-bandwidth/fill-limited when sampled by many fog puffs.
- The frozen [`func_003fb830` raster destroy L1318–1333](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1318-L1333) merely clears `slot->raster=0` and optionally restores display target, **does not restore `p4_feedback_half`**. Source-wide check found **only one code assignment** to `p4_feedback_half=0` (inside new full-base RTT allocation) and the **default declaration =1**, no code path that restores it after slot destruction. Thus **even after full RTT is destroyed and VRAM is free**, later screen-feedback draws **still take the RAM capture path** unless a separate external/manual change/reset occurs. The expected performance/quality impact is conditional on later effects actually requesting the display-raster feedback; normal gameplay or debug reconfiguration might never encounter it. **DO NOT blindly set feedback mode1 on every destroy** while any other RTT slot still occupies the feedback region; that would alias memory unsafely. Need per-slot region ownership reference count / effective resource scan, tested separately, before implementing a repair.
- Existing RTT shares main Z buffer; [`func_003f7490` L1403–1430](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1403-L1430) clears current GE target after `begin_frame` but does not independently bind raster from `camera` input. If camera `clear` is called outside matching camera-`begin`, the *currently bound* target could differ (previous REND-05 conditional risk). **Do not merge or conflate** with sticky feedback state, or claim source proves this happens on user device.

## B. Exact 2 MiB PSP VRAM layout and evidence-grounded capacity examples

Frozen [`port/rwsky.c` L22–24](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L22-L24): `SCREEN_W=480`, `SCREEN_H=272`, `STRIDE=512`. Frozen [L1202–1205](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1202-L1205): 2×RGBA display buffers + one 16-bit Z buffer, full-screen feedback copy region, tail aligned to 0x2000 bytes, end `0x200000`.

| Region | Formula from frozen code | Relative VRAM address / amount |
| --- | --- | --- |
| Two full 32bpp display buffers | 2 × 512 × 272 × 4 | `0x000000..0x110000` = **1,114,112 B** |
| One 16bpp shared depth buffer | 512 × 272 × 2 | `0x110000..0x154000` = **278,528 B** |
| Feedback base = `RTT_FULL_BASE` | display + depth | `0x154000` = **1,392,640 B** |
| Full feedback staging including edge repeat | 512 × 273 × 4 | **559,104 B** |
| Aligned free RTT tail `RTT_TAIL` | align8192(`0x154000+559104`) | **`0x1DE000`** = 1,957,888 B |
| Free tail | `0x200000−0x1DE000` | **139,264 B = 136 KiB** |

**Illustrative source-model combinations, not confirmed runtime inventory:**
- Single **128×128×32** camera texture uses **65,536B**, fits tail full size. Two use **131,072B** and leave **8,192B**; a *third* 128×128×32 would be refused, and source fallback is **draw on screen** (not merely slower resolution). A small 64×64 texture may still fit tail if correctly placed, so do not say only two RTTs ever fit.
- **512×256×16** camera texture requires **262,144B** full; default `p4_rtt_scale=0` cannot fit tail, so the source falls back to **256×128×16 =65,536B**. This is a **resolution fallback** and might affect shadows/graphics, but no actual scene-specific RTT size/format has been linked to this state in this pass.
- With **`p4_rtt_scale=1`**, first full 512×256×16 may fit the **`0x154000` full feedback region** at 262,144B; if allocated, feedback switches from VRAM mode1 to RAM mode0. It may later remain RAM-mode0 after that raster is destroyed. The worst-case performance penalty depends on actual feedback read frequency and GE pipeline; never assume **50ms** applies to a new run.
- Slot count limit 4 and VRAM bytes limit are **independent**, and `rtt_get` logs refusal only **first four occurrences** (static `refused++<4`); lack of later logs does not prove no more refusals.
- Full framebuffer/RTT overlay can share the main 16-bit depth buffer even if color target is separate. P0 GE-list bounds and bank lifetime safeguards still apply.

## D. High-information low-cost RESONANCE01 diagnostic / A/B matrix

**Before any fix or feature experimentation:** tag (bounded event ring; aggregated per camera/window):
- `RTT_CREATE`: scene/sequence, hashed Raster pointer identity, requested `w/h/bpp/type`, effective `slot index,offset,size,scale,mode`, `p4_rtt,p4_rtt_scale`, current `p4_feedback_half`, cumulative live VRAM bytes and largest free tail span; `RTT_REFUSED` count **not just first four log records**.
- `RTT_BIND/RTT_CLEAR/RTT_END`: camera id and camera+0x60 raster identity, current target, color and shared-depth write/clear state, overlay/alpha state, GE queued/finished, **don't do per-draw disk logging**.
- `RTT_DESTROY`: slot id, live full-feedback-region RTT owner count, feedback mode **before and after**, mode0 **age since owner was destroyed**. If `ownerCount=0 && feedback=0`, flag **STICKY_FEEDBACK_AFTER_RELEASE** as *observation only*; do not automatically change mode mid-frame.
- `FB_CAPTURE`: actual mode selected `feedback_half_now`, capture path (RAM/VRAM/full/half), how often per 128 accepted presented frames, CPU-side begin/end vs GE backlog and list word highwater, scene. Compare p50/p95 real-Go accepted display intervals with CPU build and late GE; recorded mode alone does NOT prove GPU bottleneck.
- **Negative controls:** no camera textures/no screen feedback (school corridor), vs Junes West F009_004, Shopping North F008_001 and Riverbed/Dream fog scenes; include sequence **fresh start→RTT full→destroy→feedback** only when naturally available with safe private saves. Record same scene/camera/ticks, cap settings. A/B require **fresh process from identical save and matched initial RTT slot inventory** for each `p4_rtt` or scale profile; merely changing a PSPLink global in-session is NOT a valid control.
- Future implementation gate **only if runtime proves** unwanted switch or error: rather than unconditional fallback reset, calculate **overlap ownership** (full-base slots count), defer change to safe frame boundary, verify no sampling/GE list still owns regions, and preserve source texture/feedback fidelity. For capacity, use memory placement simulations and real GE trace before resizing VRAM or changing depth buffers. Rollback if shadow alpha/RTT clearing, title feedback puffs, battle skill 512×256, dungeon fog, HOME/saves, or p95 FPS regresses.
