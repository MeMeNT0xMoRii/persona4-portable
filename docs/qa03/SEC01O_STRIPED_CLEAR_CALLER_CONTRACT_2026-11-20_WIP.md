# SEC-01o — striped camera-clear allocation and unchecked caller (2026-11-20 18:00 CET)

**Priority:** SEC-01 P0. **Evidence:** T1 frozen source inspection, no observed overflow/crash. **Frozen runtime:** `29b0fcfdec70222a4052099b67fb4a11e8d8aff4`. Source [`port/rwsky.c` L1380–1435](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1380-L1435).

**New exact caller-side contract:** `clear_striped(bits, colour, depth)` computes `count = ceil(target_w/32)*2`, calls `sceGuGetMemory(count*sizeof(ClearVertex))`, then writes `v[0..count-1]` without checking the returned pointer or the remaining GE-list bank capacity. The `ClearVertex` declaration has 12 bytes (u32 colour, four 16-bit coordinates), so a 480px screen clear needs **30 vertices / 360 bytes of payload**, plus the wrapper's **8-byte GE jump header** when its gated/cached path is active; a 128px RTT clear needs 8 vertices / 96 bytes plus possible header. These are arithmetic examples, not measured runtime counts. Following allocation, `sceGuSendCommandi(211,...)`, `sceGuDrawArray(...)` and `sceGuSendCommandi(211,0)` emit additional GE commands. `func_003f7490` calls this when `bits && p4_clear_stripes`, including RTT clears. A guard that merely returns NULL from `__wrap_sceGuGetMemory` is unsafe because this caller dereferences `v` immediately. Likewise a bank-capacity check limited to the 368 bytes does not reserve the post-allocation commands or `sceGuFinish` tail.

**Hypothesis T0:** high command-list occupancy before repeated RTT/scene clears can produce out-of-bounds writes, a NULL dereference if an allocator is made fallible, or GE list termination outside the bank. **Falsifier:** instrument per-bank current/end before clear, header/payload reservation, three subsequent command emissions and FINISH/END tail; run multiple scene/RTT sequences with no violation and sufficient margin, then deprioritize this path. Current evidence does not show any actual overflow.
