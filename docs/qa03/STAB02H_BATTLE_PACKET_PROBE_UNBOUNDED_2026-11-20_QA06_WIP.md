## 1. Exact original proof; this loop is NOT part of the retail packet engine

- Frozen [`port/rwsky.c` L1670–1673 and L1800–1828](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1670-L1828) executes the diagnostic block when `!(++frames & 255)`: **every 256th non-skipped draw/present call**; the code checks the global battle pointer `G32(0xb3ac-0x10000)` and, if valid-looking, traverses **four** linked packet-list heads **twice**.
- It defines `PROBE_OK(q) = (!((unsigned)(q)&3) && (unsigned)(q)-0x08800000u < 0x03800000u)`. The predicate only checks **4-byte alignment and the first byte/address lying in the PSP RAM span `[0x08800000,0x0C000000)`**. It does **not** check that the number of bytes accessed after the pointer is still in bounds, that the object belongs to a live allocation or that the list terminates. Example: 0x0BFFFFFC passes the check, but loading a `p->next` field at `p+0x7c` crosses the declared RAM upper bound.
- The first `for` reads packet fields and calls `p4_log("TRACE packet...")` **on every list element**. The second `for` reads `work`, `unit` and many coordinates, logging another line. **Both** advance `p = *(unsigned char **)(p+0x7c)` until the *next pointer* fails `PROBE_OK`. There is **no traversal cap, visited-ID check, duplicate check or budget**. A self-pointer or 2-cycle entirely within valid RAM causes unbounded iteration (and log flooding in the first pass). A pointer that looks in-range but is stale can still dereference freed/wrong-sized contents.
- Actual original PS2 [`src/Battle/btlPacket.c` L35–62](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Battle/btlPacket.c#L35-L62) defines a **`BtlPacket` with `next`, `prev`**, plus `workData`, callback functions and UID fields. Its **32-bit PSP-compatible conceptual layout** matches the diagnostic `next` location **+0x7c**, with `prev` +0x80 and entire packet at least **0x90 bytes**. However, that PS2 source does **not** establish that live packet lists are cyclic or malformed. **Avoid tampering with packet linkage/game logic just to silence the diagnostic.** This is an optional native *observer* that must not corrupt its observed system.
- On every 256th report, this same block also logs battle flags `battle+0xA44/0xA48/0xA4C`, and the second traversal reads `work+0x14` and `unit+0xec`, yet **`PROBE_OK` checks only their start addresses**. Minimum requested spans to validate before these reads: **battle ≥0xA50 bytes, packet ≥0x80 bytes for next (full packet ~0x90), work ≥0x18 bytes, unit ≥0xEE bytes**; these are *memory-range* minima, NOT proofs of allocated-object size. `G32` battle pointer, list-head pointers and after-GE watch must be tagged with source ID and real linked PSP code. The issue exists independently of GE list overrun.

## 2. How this could confuse STAB-02 diagnostics, and what it cannot prove

A malicious/corrupted or legitimate unexpectedly circular `next` chain could make native port **tracing** hang even if the original PS2 gameplay task is not stuck. If a battle has a valid-looking stale pointer in that chain, the probe could fault; any resulting PSP Go hang might be misattributed to `btlUnitInitChild`, an asset load, or the GE watchdog. At minimum a long valid chain generates unbounded logs and per-256-frame CPU/I/O costs; frozen `port/main.c::p4_log` uses a 64KiB text ring but can fall back to **synchronous** storage on logger thread creation failure. Conversely, ordinary battles with well-formed short null-terminated lists may never show a problem. **Whether this route is ever hit at the user's reinforcement freeze is T0**, and even a cyclic chain would need independent proof it was invalid rather than expected sentinel structure.

This is **not** a fresh evidence-backed explanation for the real edited-save freeze, simply a critical forensic observer-safety blind spot.

## 3. Narrow Codex implementation choice, separate from actual battle logic

1. **First establish effective linked build and battle packet topology**, including `btlPacket` allocator ownership, list-head sentinel/null semantics and whether this native `TRACE packet` path is active during the user's test. No broad gameplay/recomp patch based solely on an unsafe observer.
2. **SAFE REGULAR candidate:** remove or compile-gate the periodic deep packet trace (only diagnostics, not game packet updates) if verified unused for game functionality. Retain low-overhead event/count summaries separately; preserve reproducibility of perf06 control and baseline log cadence. If no source/runtime proof of safe-off, defer changing it until actual A/B testing.
3. **DIAG-LITE candidate:** replace the *observer only* with explicit `uintptr_t` range+byte-length guards **before every load** (at least battle 0xA50, packet ~0x90 or exact inferred size, work 0x18, unit 0xEE). Limit to a measured small number of nodes per list per diagnostic window (e.g. provisional 16 or 64), add `CYCLE/SUSPECT_POINTER/TRUNCATED` counters or visited-prefix set, record only `head, count, reason, last valid stage` in the fixed binary ring. Do not stream text for every node. An address in the RAM span is still not proof of live allocation; if ownership metadata inaccessible, record **`UNVERIFIED`**, do not dereference unsupported pointers. Never follow raw `next` from a GE interrupt.
4. **Testing:** synthetic self/2-cycle, long chain, end-of-RAM boundary, unaligned/outside/stale-looking pointer, genuine short null-terminated chains; **then** build/PPSSPP safe normal battle vs reinforcement from three cloned saves, compare regular and diag-lite with 256th-frame traces and CPU p95. In real PSP Go test, do **not** deliberately inject corrupted packet pointers, no source save mutations.
5. **Rollback:** removal/gating of debug-only telemetry must not change any original battle packet execution, 1–4 party HUD, attack/skill transitions, sound or input, GE bank retirement or frame pacing. On real device if packet count seems large or mixed topology is unknown, record a bounded summary and stop tracing, not a speculative repair.
