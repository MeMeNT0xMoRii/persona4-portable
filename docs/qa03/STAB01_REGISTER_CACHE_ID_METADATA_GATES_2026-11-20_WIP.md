## Source-read evidence, with exact provenance

- Original [`src/Yajima/y_list.c`, `yListSlotRefresh` FUN_002E4090 L663–735](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L663-L735), `case 6`: for each **active roster slot**, copies a 0x30-byte current record, reads `((YListPersonaMetadata*)iGpffffb3d4)[current.id].arcana` **before** validating the ID, and **if `arcana < 0x16`**, unconditionally `memcpy(&registered, datPersonaCachedRecord(current.id), 0x30)`. It then compares records via `yListRecordsDiffer` and appends changed roster entries. Both metadata lookup and nullable cache pointer have potential unsafe preconditions independent of frame-rate/GPU.
- Original [`include/datUnit_internal.h` L67–83](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/include/datUnit_internal.h#L67-L83): `DatPersonaRecord.flags` and `.id` are **u16 at offsets +0/+2**, size **0x30**. An edited roster can therefore encode ID values **0x0100..0xFFFF**, outside the cached Persona ID domain; byte-only validation would miss these. The actual length of the external `iGpffffb3d4` metadata resource was not measured here, so do **not** assert a specific out-of-range address or guarantee a crash: the **unvalidated metadata read** is the exact T1 finding.
- Original [`src/Yajima/y_list.c` L100–108](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L100-L108): `YListPersonaMetadata` has **14-byte stride**, flags u16 at +0 and arcana u8 at +2. Metadata must be **verified for a valid ID before lookup**; checking only the arcana is not an ID check.
- Original [`src/g_data/g_data.c` `datPersonaCachedRecord` FUN_0010FCB0 L2693–2711](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/g_data/g_data.c#L2693-L2711): asserts `0 <= id < 0x100`, returns cache record only if its **own record `flags & 1`** is set, else **NULL**. A valid ID (e.g. <256) with an **inactive cache** is a real null-source `memcpy` precondition. Roster active bit and cache active bit are separate `DatPersonaRecord` storage, **not** automatically equivalent.
- **New eligibility reconciliation (T1):** Original [`datPersonaInitAllRecords` FUN_0010FFA0 L2786–2836](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/g_data/g_data.c#L2786-L2836) iterates **IDs 1..255**, seeds **missing cached records only when metadata flags have neither bit `0x8` nor `0x20`**. For records with `(metadata.flags & 0x28) != 0`, it **does not seed**, even though Register's `case 6` only checks **`arcana <22`**. This is a structural potential mismatch, *not* evidence that a specific excluded-class Persona actually has arcana below 22, appears on the user's roster or is not already in cache. **ID=0 is never initialized in this routine**, another discriminator for an edited roster even though `datPersonaCachedRecord(0)` accepts the range.
- **Second unsafe consumer:** Original [`src/Yajima/y_list.c`, `yListSlotSortByKey` FUN_002E6C90 L1941–2005](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1941-L2005) builds `sortedIds[]`, zeroes destination, then copies **0x30 bytes unconditionally** from `datPersonaCachedRecord(sortedIds[writeIndex])`. [`yListSlotSortWeighted` FUN_002E68B0 L1790–1858](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1790-L1858) has the **same unguarded cache-copy pattern**. Verify which sort/refresh is actually called at the failure, rather than patching a single memcpy and assuming all Compendium flows are safe. Sort arrays are `s16 sortedIndices[256]` and `sortedIds[256]`; normal list count likely below that limit, but no executed count trace from modified saves.
- **Trap: not a safe automatic fallback.** [`datPersonaResolveRecord` FUN_0010FDE0 L2728–2782](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/g_data/g_data.c#L2728-L2782) returns the input record unchanged when metadata flags include 0x8 or 0x20, or returns the existing cached record; on a missing, eligible record it **copies bytes into the cache then returns NULL on that same invocation**. Therefore simply substituting `datPersonaResolveRecord` as memcpy source would still crash under one branch. Also avoid modifying cache/save as part of an initial logging experiment.

## Exact behavior decision matrix — hypotheses to discriminate with private save copies

| Active roster record state / metadata | Source branch | Predicted danger | What first diagnostic must capture |
| --- | --- | --- | --- |
| `id >=256` (16-bit) | Register indexes metadata **before** cache assertion | Unvalidated metadata lookup; if arcana passes, cache asserts invalid ID | `slot, id, metadata resource extent if known` **before** any index |
| `id = 0` | Valid ID range, but `InitAllRecords` starts at 1 | Potential cache inactive/null if no other seeding | Cache flag, roster flag, explicit sentinel handling |
| `id = 1..255`, `arcana >=22` | Register skips cache comparison | No NULL in this branch; later sorting/other flows still require audit | `arcana, skipped=1` |
| `id = 1..255`, `arcana <22`, cache flags bit0 = 0 | Register unguarded copy | **NULL source 48-byte copy**; can fault | `kind=6, slot,id,cache.active=0,phase=pre-copy` |
| `id = 1..255`, `arcana <22`, cache active | Register compares 0x30 bytes | No NULL source in this call, but content/semantic integrity still unknown | `cache.flags, cache.id, current.id, diff` |
| `id = 1..255`, metadata flags `0x8/0x20` | `InitAllRecords` intentionally excludes normal cache seeding | **May** remain cache-inactive even when Register's arcana gate admits it | `metadata.flags &0x28`, `arcana`, cache.active, whether cached by other path |
| Any list route invoking `yListSlotSortWeighted` or `SortByKey` with a sorted ID lacking cache | Sorted row `memcpy` | Independent null copy regardless of Register case | Exact sort function, `kind`, `sortedIds[i]`, `count`, cached flags |

**No user-save bytes were inspected in this audit.** A real freeze might be elsewhere (metadata corruption, task deadlock, GE overrun). A missing cache pointer is only a **static, falsifiable precondition**, not root-cause proof.

## Safest first test and later engineering gate

1. Compare **three PRIVATE cloned saves**, unchanged original (A), minimally edited (B), complex modified reportedly failing (C); preserve source hashes and `.bak`. **Never call a cache-seeding function in a read-only classifier.** If no save parser is trustworthy, instrument original-runtime access in a separate diagnostic build only after explicit permission; source saves stay untouched.
2. Before **any** metadata dereference: log `save_cohort, roster_capacity, slot, roster.flags, u16 id, id_in_0_255, metadata_known_valid`. Only if ID valid: log `metadata.flags`, `arcana`, `cached_record.flags bit0`, `cache.id` (if active), `stage=refresh/weighted-sort/key-sort`, row count; bounded logs avoid PSP audio/IO stalls. For cache missing, **do not dereference** in the diagnostic code. Distinguish failure *at* list creation vs sort input/caller.
3. Repeat only requested Compendium **Register, Withdraw, Release, Sort** menus and normal/minimal/complex saves. Require first diverging `slot/id/cache` tuple and isolated callsite before proposing any guard; no blanket mutation of all Persona records, no automatic `datPersonaInitAllRecords()` call during Register.
4. Future local fix concept (requires separate authorization, host tests, PPSSPP T2 then PSP Go T3): validate 16-bit ID first; clarify excluded Persona policy with original Vanilla; decline/quarantine or present a safe placeholder when cache missing *without mutating saves*; protect both sort paths; preserve list count/cursor order and exact vanilla behavior for valid cached records. Explicitly test cache table `256*0x30=0x3000` bytes and boundary IDs 0,1,255,256,65535 plus normal and excluded flags. An abort, changing roster data or blindly copying the current record into Compendium would undermine gameplay.
5. **Regression controls:** native PSP Go register/withdraw/fusion/Compendium order, no accidental inventory loss, HOME, `ef0:/` save backup/rollback, exact perf06 runtime/manifest hashes and no GPU-state changes. No "fixed" status until a copied failing save actually passes hardware acceptance.
