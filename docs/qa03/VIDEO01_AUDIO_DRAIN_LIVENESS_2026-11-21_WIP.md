# VIDEO-01 — Audio drain liveness on cutscene exit (2026-11-21 02:00 CET)

**Evidence:** T1 static code only, frozen gameplay source `29b0fcfdec70222a4052099b67fb4a11e8d8aff4`. [`port/video.c` L62–91](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/video.c#L62-L91) audio worker calls `sceAudioOutputBlocking` and, after EOF or `stop_audio`, executes `while (sceAudioGetChannelRestLen(channel) > 0) sceKernelDelayThread(1000)` without deadline or stop/error escape. [`p4_video_play` L323–339](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/video.c#L323-L339) sets `stop_audio=1` and then calls `sceKernelWaitThreadEnd(audio_thread,NULL)` without timeout. Thus a channel reporting a permanently positive remaining length can prevent cutscene cleanup from returning. This is a **conditional liveness hypothesis**, not a reproduced firmware failure or proof the channel can stick. The separate `sceAudioOutputBlocking` call can also block; merely bounding the final rest-length loop does not bound all worker termination.
