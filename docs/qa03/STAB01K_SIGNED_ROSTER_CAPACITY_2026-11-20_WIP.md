# STAB-01k — signed roster loop counter vs unsigned 16-bit capacity (2026-11-20)

**Evidence T1 (static only), priority STAB-01.** Original pinned `Raikaru/Persona4-Decompilation@363eab8a966d60a9773b45f330f2344329ec4f0a`, [`src/Yajima/y_list.c::yListSlotRefresh` lines 664–746](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L664-L746): local `slotIndex` is **s16**, whereas cases 1, 5 and 6 loop against `(datPersonaRosterCapacity() & 0xFFFF)`. No local explicit guard clamps capacity to either the **253 roster entries** available in the 0x3014-byte work buffer or the **signed 16-bit counter** maximum. The count increments only for selected records, but the loop index increments for *every* roster slot. If an invalid capacity exceeds 32767, incrementing s16 beyond its range has implementation/compilation-dependent behavior and can wrap or fail to terminate; it can also reach invalid roster-slot addresses long before that. **This is conditional, not proof of a corrupted actual save or a freeze**. It is distinct from STAB-01j's work-buffer row-count bound and from the previously known NULL cached-record in kind 6.

**Negative control / falsifier:** trace the actual capacity returned by `datPersonaRosterCapacity()`, its signed/unsigned comparison representation, loop index, active count and final work offset on pristine and private edited-save Register paths. If capacity stays within normal roster limits and the loop terminates, this signed-counter hypothesis is ruled out for that reproduction. Do not assume edited Persona IDs imply a changed capacity. For kind 6 also trace metadata ID and cached-record presence, separately; do not upload save content. Compare kind 1/5, Register kind 6, normal compendium kind 2 and save/HOME. Stop diagnostic trace safely before invalid dereference; preserve original gameplay behavior in regular builds.
