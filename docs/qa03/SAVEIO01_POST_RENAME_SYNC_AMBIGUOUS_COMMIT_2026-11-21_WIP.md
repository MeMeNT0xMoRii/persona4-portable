# SAVE-IO-01 — post-rename sync failure is an ambiguous save commit (2026-11-21 05:00 CET)

**Priority:** save/HOME integrity, below B0/SEC-01 and before optional UI/performance. **Evidence:** T1 frozen static control flow; actual device failure T0, no T2/T3.

**Frozen source:** [port/memcard.c::func_00432288 L139–187](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/memcard.c#L139-L187) at `29b0fcfdec70222a4052099b67fb4a11e8d8aff4`. It writes a .tmp, flushes/closes and syncs, optionally removes prior .bak, renames primary to .bak, then renames .tmp to primary. **After a successful rename**, it calls `sync_card()` again and returns `MC_IO` on sync failure, without rolling back the now-installed primary. This creates a distinguishable *ambiguous commit outcome*: game may report failure while a new primary exists. It is NOT evidence that the file is durable after a failed sync, nor evidence of corruption. The current `open_saved` fallback reads .bak only when primary fopen fails, so the next load may read new primary even after the failed save report. Source owner `port/memcard.c`; storage path `port/paths.c::p4_paths_init` supports `ms0:/` and `ef0:/`. This is unrelated to UI save-slot geometry owner.

**Hypothesis/falsifier:** On a PSP Go with transient `sceIoSync` failure after final rename, a retry or UI error could disagree with installed data. Falsify the scenario's practical reach with bounded instrumentation showing successful second sync under all exercised normal saves, and a deterministic mocked second-sync failure demonstrating actual state/return. Do not infer actual physical persistence from a mocked return.

**Minimal test:** Host fake filesystem/sync layer inject failures separately at (a) pre-rename sync, (b) backup rename, (c) temp->primary rename, (d) post-rename sync; inspect primary/.bak/.tmp bytes and reported status for each. Negatives: normal save, overwrite, read backup after interrupted rename, two consecutive saves, both `ms0:/` and `ef0:/`, HOME during save. On actual Go use disposable test saves only, never overwrite private user saves. Record each phase and avoid retries that might delete the only good backup.

**Candidate, not approved fix:** Explicitly represent 'commit installed but durability unknown' in diagnostics; design a recoverable transaction/reconciliation state before changing PS2-facing error semantics. **Cost:** low host fault-injection, moderate PSP lifecycle and save-compatibility risk. **Rollback:** any changed slot visibility, save checksum, missing backup, storage regression, or hang. **Cross-rotation:** consulted `PERF06_RUNTIME_BASELINE_FORENSICS_WIP.md`, frozen `port/paths.c` and `port/memcard.c`; perf06 save-device sync is already enabled and must not be removed. Private regular perf06 EBOOT bytes unavailable; no builds, runtime changes, T2/T3 or FPS claims.
