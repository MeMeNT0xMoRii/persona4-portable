# QA03 — Practical PPSSPP unattended playthrough and bug-bisect bot, V2 source-backed architecture

Date 2026-11-19. This is a feasibility/engineering spec, **not a running test bot, not a service started on the user's PC**. It is designed for local authorized PlayStation Portable builds with private original-game resources and private save states. Keep all game data, memory dumps, save states, voice/music and screenshots outside public GitHub.

## Concrete available test interfaces — no invented PPSSPP API
Verified upstream [hrydgard/ppsspp master docs/WebSocketDebugger.md](https://github.com/hrydgard/ppsspp/blob/master/docs/WebSocketDebugger.md#L276-L306) includes a JSON WebSocket debugger listening on /debugger with the debugger.ppsspp.org subprotocol, enabled by --debugger=PORT. Official current public [PPSSPP WebSocket API](https://www.ppsspp.org/docs/reference/websocket-api/), [command-line](https://www.ppsspp.org/docs/reference/command-line/) and [developer docs](https://www.ppsspp.org/docs/development/getting-started/) support both GUI and headless builds.

Important: master docs [lines 284–300](https://github.com/hrydgard/ppsspp/blob/master/docs/WebSocketDebugger.md#L282-L301) identify:
- game.status, game.reset and **game.state.load/save/verify**, game speed; do not rely on older third-party MCP bridge docs claiming savestates are absent.
- input.buttons.send, input.buttons.press and input.analog.send; inject *timed and acknowledged* stable button edges, not random simultaneous presses.
- memory.read_u8/u16/u32, memory.read, memory.search; cpu.breakpoint.add and register/memory breakpoints; log subscriptions.
- gpu.stats.get/feed, gpu.displaylist.disasm, gpu.buffer.screenshot/renderColor/renderDepth/renderStencil, gpu.record.dump, and hle.thread.list.
- For headless execution, --debugger=PORT and --state=FILE (precise compatibility needs run/CLI validation); official PPSSPP docs mention a .ppst boot path. Host OS process exit, crash and watchdog remain separate from emulator error responses.

**Local test harness first:** check the installed PPSSPP version/build actually accepts each event and output fields, and run one harmless API probe on a clean homebrew or P4P intro, never assume master API is in every release. WebSocket debugger writes arbitrary emulated memory; bind to localhost, no remote exposure and no game memory tampering outside controlled debugging.

## Minimal architecture (future approved implementation)
1. **Session manifest:** exact P4P EBOOT SHA256, input game data identity, git source commit and build profile; PPSSPP build/backend/graphics mode, PSP model/memory, clock, seed, UTC/local time, save-state SHA256, path and checkpoints. Reject mismatched build/save pairs before a replay.
2. **Scenario DSL:** deterministic scene snapshots and conditions (intro→title, load save, school transition, Junes West, battle, reinforce, Apsaras fusion, Compendium, social link, shop and dungeon). A scenario defines input action + duration in *emulated frames/ticks*, precondition proof from game state or visual anchor, maximum wall/emulated time and known checkpoints. No blindly repeated circle/cross at a confirmation dialog.
3. **Controller:** run PPSSPPHeadless for non-visual state machine and GUI/renderer runs when screenshots are required; use websocket input event, then assert memory/scene hook or bounded image hash. Inputs/snapshots and random source pin; repeat results with default and software renderer as a discriminator, not a hardware performance replacement.
4. **Breadcrumb ring:** last 120 emulated frames of scene/state/input, last 256 on-screen render passes or budgeted aggregate stats, GE list words and watchdog periods, game task ID, asset loader state, current save metadata and last successful checkpoints. Persistent log flush on checkpoints/crash, bounded memory and rate to avoid lowering FPS. Do not dump full private memory to public issue.
5. **Stall classification:** distinguish app crash (host exit), debugger connection closed, alive-but-no-state-advance (maybe blocking dialogue), CPU/main-thread busy, asset loader wait, GE no-progress and vblank/present stuck. First sample heartbeats, current PC/thread stack if safe, GE head/tail and log tail; on abnormal stop, capture state snapshot and exact input script.
6. **Repro/bisect:** resume last safe checkpoint with copy of save, try previous/next commit only after building compatible EBOOT in explicitly authorized environment; compare frozen input and private assets, emit minimal repro and suspected source path. A fix that passes this checkpoint must also run earlier checkpoint(s) to detect regressions.
7. **Graduated route:** (A) intro/title and XMB HOME, (B) school/Shopping District/Velvet before progression, (C) first battle/save, (D) multi-dungeon and repeated transitions, (E) broad chapter playthrough, (F) actual credits. Full narrative automation requires **decision scripts, encounter handling, healing/equipment, failure recovery, state oracles**; no claim that video-only random driving can finish a hundred-hour RPG.
8. **Hardware feedback:** PPSSPP is diagnostic for game logic, GPU state and deterministic regression; actual PSP Go 333MHz has different GE/VRAM/CPU/IO and remains performance/stability truth. Never infer 20/30 FPS from unlimited/headless emulator.

## Concrete first standalone test for next approved coding session
Use clean private prepared game and original save; boot to title with --debugger, obtain game.status, inject confirm press then release, confirm top menu state; save state using game.state.save (if installed PPSSPP version supports), reset/load, check game scene and deterministic input, capture screenshot and GPU stats. Test failure: deliberate short timeout at idle menu should yield **non-crash dialog wait classification**, not false positive 'freeze'. No game source patches needed for first API feasibility probe if local PPSSPP can be launched.
Then test one Junes/Velvet checkpoint and controlled crash/hang using a **separate synthetic homebrew program**, never deliberately corrupt user's real save. Compare bot output, stop conditions and recovery before integrating with automated build cycle.

## Provenance and restrictions
Public upstream [PPSSPP docs/WebSocketDebugger.md](https://github.com/hrydgard/ppsspp/blob/master/docs/WebSocketDebugger.md) code API is authoritative; third-party tools such as MCP bridges may have stale event catalogs. Keep HTTP/WebSocket credentials/local bind private. Run bounded tests only when started/approved by the user, or in a correctly configured and authorized environment; the existing hourly QA research automation **does not own a persistent GPU process or guarantee overnight real PSP tests**. Read queue PRIO QA-01 and HANDOFF_LIVE before repeating research.
