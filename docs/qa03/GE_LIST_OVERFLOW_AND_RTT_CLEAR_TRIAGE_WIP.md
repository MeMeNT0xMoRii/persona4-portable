# QA03 — P0 GE display-list capacity, camera projection and offscreen-clear safety (code-first)

**Verified 2026-11-19.** Current game baseline: `MeMeNT0xMoRii/persona4-portable`, `dev/v0.27-perf06`, **runtime commit** `29b0fcfdec70222a4052099b67fb4a11e8d8aff4` (later branch changes include docs and PPSSPP lab helper, not a new EBOOT). Compare upstream `dreikk91/persona4-psp@b388`, and original PS2 `Raikaru/Persona4-Decompilation@363eab8a966d60a9773b45f330f2344329ec4f0a`. T1 = static source condition verified. **No game-source/runtime edits or builds, no emulator / PSP Go run, no measured overflow, no proven crash fix.** This audit is public text only; private saves/screenshots remain private.

## P0-1: 64 Kiword GPU display lists with unbounded allocation path (confirmed T1 hazard, user crash attribution T0)

**Current P4P exact source**:

- [`port/rwsky.c` L458–464](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L458-L464): `static unsigned list_store[2][64 * 1024]` stores two **65,536 32-bit-word** buffers, **262,144 bytes each** (524,288 bytes total). These are **main RAM** GE command buffers, **not** the PSP's 2 MiB eDRAM framebuffer. `list_to_cached` [L697–710](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L697-L710) uses `sizeof list_store[0]` for tracking cache-flush bounds, not a guard against actual draw-list overflow.
- [`__wrap_sceGuGetMemory` L1900–1918](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1900-L1918) takes current `gu_list->current`, advances by `size+8`, writes a GE jump header and returns a vertex-memory pointer **without testing end-of-list capacity**. When `gate_closed` or cached list is enabled (default `p4_list_cached=1`), this wrapper is used; otherwise it calls libpspgu's native allocator. Many draw sites allocate via `sceGuGetMemory` (2D, clear, particle/Im3D and others). Direct `gu_list->current` writes outside the wrapper also exist, so a wrapper-only guard cannot ensure global bounds.
- At frame rollover [L1590–1616](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1590-L1616), the two list buffers alternate in pipelined mode. No `LIST_WORDS/LIST_RESERVE` size guard, `list_room()`, overflow high-water count or draw refusal exists in `port/rwsky.c` on the pinned P4P runtime.
- **Upstream control**: [`dreikk91/b388` `port/rwsky.c` L82–90](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L82-L90) uses `LIST_WORDS = 128*1024` (131,072 words, 524,288 bytes/list), **1,048,576 bytes total** allocated via `memalign` [L652+](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L648-L662). [`list_room()` L319–327](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L319-L327) reserves **4,096 words** for tail operations and rejects selected draws, and logs peak/close-to-full [L1225–1235](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L1225-L1235) / per-256-frame summary [L1425–1430](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L1425-L1430). Upstream comment explicitly reports **fog battles up to 67,927 words** with old 65,536-word lists, after which adjacent memory became corrupted and crashes appeared in **`btlUnitColorPacketUpdate` and `sdkOtFlushBuckets`**. This is *upstream PSP measured evidence*, not evidence that the user's exact modified-save freeze is this overflow.
- Thus under similar draw workloads, P4P may overrun a fixed list with undefined memory corruption; a too-small display list is now a **high-priority crash/visual corruption candidate** for fog battles, sudden freezes and intermittent drawing anomalies. It is **not** a proven cause of Junes 12FPS or Compendium Register crash (which has its own independent NULL risk).

**Proposed safest progression, once execution is approved**:

1. In an *isolated debug build*, install a minimal, non-reentrant **high-water/remaining-words metric** at frame finalization and before allocating command words, checking actual list base/current and projected allocation against the list capacity; check wrappers **and direct raw-word writers and libpspgu calls**. Include source scene, GE list index, frame ID, pipeline mode, `words_used/words_peak`, `overflow_prevented`. Consider an early fail-safe with clear diagnostic rather than writing outside the array. **Simply refusing one draw is not universally safe**, because unbalanced GE state and lost allocations can break visuals; define robust error handling.
2. Reproduce **fog-heavy battle, transitions to reinforcements, first+second fusion, Junes West, Yomotsu/castle and menu-title** with a clean original save and separately modified saves. Use stock perf06 for baseline **only where safe**; don't intentionally force a likely-corrupting overflow on user hardware. PPSSPP debugger or isolated host layout stress tests first, and copies of save media only.
3. If high-water threatens 65,536, test **128Kiword double-buffer lists** in a reversible candidate as b388 did, but allocate only after checking **main RAM** headroom, `.bss` position relative to fixed `.p4image` and heap alignment. This consumes **additional 512 KiB main RAM**. Move from `.bss` to heap if required to avoid retail data collision, preserve 64-byte alignment, both pipeline halves, cache-flush tracking and GE stall correctness. Never blindly double static arrays in-place.
4. Preserve crash logging: dump current pointer/base before any unsafe write, GE list ID/status, last task and draw class; do not assert “fixed” without PPSSPP and PSP Go T2/T3 plus 30-minute varied combat/fog/UI route and memory/peak logs. Do not conflate b388's guard with a formal guarantee that **all** upstream GE writers are bounded: audit all relevant paths after cherry-pick.

## P0/P1-2: camera CLEAR before camera begin-update uses wrong target in perf06 (T1 conditional bug)

- P4P [`func_003f7490` `port/rwsky.c` L1403–1430](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1403-L1430) receives `camera` but **does not inspect that camera's raster**. It clears whatever target the current `rtt_target`/GE draw-buffer already happens to represent. Camera render target selection is made on [`func_003f6a10` begin update L1345–1369](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L1345-L1369), **after** a pre-update clear in certain game paths.
- b388 [`func_003f7490` L1127–1160](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L1127-L1160) fixes precisely this: `was = rtt_target`, `own = rtt_get(*(Raster **)((char*)camera + 0x60))`, switch to `own`, clear, restore `was`. Upstream [`visual_issues.md`](https://github.com/dreikk91/persona4-psp/blob/b388/docs/visual_issues.md) documents how stale silhouettes accumulated in Junes and Living Room before b333.
- If a Vanilla camera requests a clear **before** its begin update and `own != current target`, current P4P clears the wrong raster and leaves the intended RTT's previous content intact. This is an **exact conditional code-path discrepancy**, not hardware-confirmed user-visible shadows in perf06. Keep `rtt_clears` accounting to actual target, preserve render state and global target after clear, and do not globally clear both framebuffers.
- **Test:** log camera address/type, `camera+0x60` output raster, `rtt_target` before, intended RTT, clear mask, associated 128×128 RTT, and a two-consecutive-frame GE texture read using PPSSPP software renderer/debugger. A fix to clear targeting alone will **not** restore the shadow unless projection and Im3D quad/DATE/fade are also correct; different passes must be tested independently.

## P1-3: orthographic projection absent, camera state-cache key coupling (T1, conditional)

- Current [`camera_projection` L3770–3777](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L3770-L3777) always emits perspective. Upstream [`guard.h` L128–145](https://github.com/dreikk91/persona4-psp/blob/b388/port/guard.h#L128-L145) checks `camera+0x14` (projection type 2 = parallel), uses non-perspective matrix for Junes floor RTT. Fix must propagate through **GE projection, CPU guard/model-to-clip maths and cache**; not only shader-looking output.
- In P4P [`set_camera` L3779–3801](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L3779-L3801), the mesh-state camera cache key includes camera pointer, view rotation/translation and near/far but **not `camera+0x14` projection type**. If projection type can change in place on the same camera without those other fields changing, the cached perspective/orthographic projection could remain stale after implementing support. That is a **conditional correctness pitfall** to audit, not a measured failure today; invalidate/bind projection mode appropriately in the scope of the patch, and preserve fast path when unchanged.
- Current [`im3d_caller` L11145–11166](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L11145-L11166) **rejects nonindexed field-shadow draws** unless `shuffle_nonindexed`. b388 [`im3d_caller` L2994–3003](https://github.com/dreikk91/persona4-psp/blob/b388/port/rwsky.c#L2994-L3003) includes **only nonindexed Im3D with `rtt_find(render_state[1])`** when `p4_field_shadow` is enabled. Other b388 RTT shadow fixes include **clamp instead of repeat**, alpha/DATE fade routing and clearing *the correct* target. Respect each as a separate test; a blanket Im3D enable could break unhandled pipelines and consume FPS.

## P1-4: performance and UI tradeoffs (do not solve a crash by dropping fidelity)

- P4P `p4_pipeline=1`/frameskip are already active; [`p4_exp_ge_time` L2109–2174](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/rwsky.c#L2109-L2174) **serializes** GE and cannot provide a stock pipeline FPS A/B. Need per-scene CPU time, GE wait, real presented frames, p50/p95 and list high-water **in the unchanged build** before a performance patch.
- P4P **feedback/destination-alpha** writer/readers are a separate cost and visual problem (`p4_dst_alpha_passes=0`, `p4_alpha_pixel=0`); b388's fusion glow mechanism has distinct clear/RTT/alpha traces. Never “fix” a perf regression by globally skipping more VFX, fog or draw classes: that would further alter Zio, Apsaras and Dungeon effects. Keep b383/b386 culling isolated from list allocation and shadow-camera changes.
- Proven UI owner of bottom-left command wheel: original `btlSelectionDrawCommands` **FUN_00207B00**, not central panel `FUN_00203930`; UI-A circle yscale test and UI-B/C/D/F local anchors remain independent from all renderer guard experiments. The increased Y radius can bring the outer wheel near bottom edge; measure it before combining with GE-list changes.
- **Current P4P memory documentation** [`PSP_HARDWARE_LIMITS_WIP.md`](PSP_HARDWARE_LIMITS_WIP.md) and [`port/main.c` PSP heap settings](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/main.c#L1-L33) prevent treating 64MiB as free. B388 docs report sometimes `.bss` approached fixed game image; a larger static array may shift other content.
