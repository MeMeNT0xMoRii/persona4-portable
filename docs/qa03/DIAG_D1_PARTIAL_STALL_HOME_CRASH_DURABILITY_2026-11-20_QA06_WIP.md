# QA06 — D1 Flight Recorder blind spot: zero-POST hard stalls, HOME exit, per-device durability and GE bank provenance (20 Nov 2026)

**Evidence:** direct original C host-model read + frozen PSP T1 source, no PSP test or real user crash diagnosis. P4P runtime remains frozen at `29b0fcfdec70222a4052099b67fb4a11e8d8aff4`. This audit identifies a reproducible **state-machine limitation from code**; it does not prove a specific user-observed enemy wave/Compendium freeze has this cause. Read before Saturday RESONANCE01 Diag-Lite integration.

## 1. Source-proven highest-priority gap: after an immediate hang the model never SEALED

Exact committed [`docs/qa03/host_tests/p4diag_host_v1.c` L35–79](host_tests/p4diag_host_v1.c), blob `be49fdf125e99a31681174a6fab2a749c54de485`:
- The protocol `ROLLING → CAPTURING → SEALED → EXPORTING → ACK` is a **host-only C model**. `ring_trigger()` sets `CAPTURING`, snapshots up to 128 preceding records and sets `post_count=0`. Only `ring_push()` increments `post_count`, and it transitions to SEALED **only when exactly 128 subsequent events arrive** (`++post_count == POST`).
- The reporter `export_begin()` calls `ring_validate()`, which unconditionally checks `post_count==POST`; `parse_file()` expects at least one record. Therefore **the current model has no API/path to seal and export a valid 0..127 POST capture**. If the failing game path immediately stops emitting events, the most important captured PRE events may stay only in volatile RAM, never becoming a persisted incident. The earlier **23/23 host tests all passing is correct but does not cover this case**; one of their setup helpers always adds 128 POST events.
- If a very early trigger occurs with zero preceding records and no subsequent event, `ring_count==0` and the current parser rejects a zero-record file. A partial-seal implementation should append one typed trigger/timeout record or design an explicit empty-event envelope; never underflow `start_seq+count-1` and call it a valid snapshot. Normal full-POST behavior, sequence wrap and CRC checks must remain unchanged.
- During `SEALED/EXPORTING`, `ring_push()` rejects all new events and increments drop count, so stalled storage can leave the sole ring permanently unavailable. Track `SEALED_AGE`, drops/missed trigger reasons, failure and retry policy. A second independent tiny emergency breadcrumb buffer may be justified **only if RAM/headroom and contention permit**; not in the unmeasured regular build.

**Minimal Saturday implementation proposal (not tested):** attach an independent *safe background worker/watchdog* to game-progress heartbeat (`tick_seq`, task-stage, GE submission and **accepted display** are different signals). If a trigger is already CAPTURING and game progress has not advanced for a bounded, initially configurable timeout, seal the **actual 0..127 POST** length with a `PARTIAL_CAPTURE|NO_GAME_PROGRESS|TIMEOUT` flag and current stage. The worker must atomically snapshot the ring's logical indices/records under a very short lock/interrupt-safe section, perform binary writes **after releasing it**, never call blocking disk IO from GE callback/interrupt or gameplay lock. If only render/display stalls but CPU game ticks progress, distinguish before labeling; a scene load or deliberate pause may legitimately lack ticks: classify `suspected stall`, not proven deadlock. Proposed timeout is a test knob, NOT a validated PSP threshold.

## 2. No filesystem protocol can guarantee a record survives a total PSP freeze or power cut

| Failure class | What is possible if scheduled worker still runs | What remains unguaranteed |
|---|---|---|
| Slow frame, game continues, >=128 POST events | Full 256-event sealed incident; bounded worker may export complete snapshot | Whether storage is durable until actual verified file/device sync |
| Game task permanently hangs, worker scheduler alive | Independent heartbeat timeout can **partial-seal** and *attempt* a disk export, if locks/IO remain operational | Hard freeze cause, whether GE/OS locks also block writer, or storage is writable |
| GE pipeline stalls but game task advances | Separate queued/finished/display progress flags; partial seal based on affected signal, not only task heartbeat | GPU execution time, root cause inferred from co-occurring counters |
| Whole process/kernel or firmware deadlocks | Last **previously committed** journal record might survive; PSPLink savemem only if debugger/USB/RAM still accessible | Live RAM ring or new export after scheduler stops; cannot guarantee any post-crash persistence |
| Abrupt power loss / hard power off | Previously synced files *may* survive subject to storage semantics | The unflushed 100ms of text logging and any unsynced sealed D1 incident are lost; no guarantee against media failure |
| HOME confirmed during capture/export | Optional documented safe-point preexit flush if proven bounded and storage available | Frozen HOME callback exits via `sceKernelExitGame` without coordinating the proposed Diag-Lite worker, so do not promise a completed incident on immediate HOME |
| Storage full / write error / short write | Keep pending snapshot in RAM **while process remains alive**, bounded retry and explicit drop/errors | RAM state disappears on exit/power; no magically persistent `SEALED` state across relaunch |

Do not claim `persisted_and_verified` host boolean means PSP disk sync or reopen-readback was executed. The [C reference model](host_tests/p4diag_host_v1.c) L75–80 / L120–150 uses caller-supplied `persisted_and_verified` and a mock RAM sink, **not a real `sceIo*()` writer or device durability proof**. It checks CRC/schema of an in-memory file only. Required genuine PSP writer behavior: write complete temp with checked short/zero/negative returns, close/check, sync correct `ms0:/` or `ef0:/` volume, reopen/readback CRC and length, safe rename / sync, verify the final named file, then ACK and reset RAM incident; on error keep original sealed snapshot in RAM and do not claim external persistence. On startup, independently scan and validate any abandoned temp/final file with strict bounded length/schema and do not silently delete a valid older incident. **Even verified and synced write is best-effort against actual physical removal/power cut**.

## 3. Source-proven HOME and text-logger interaction: do not inherit the save lock accidentally

- Frozen [`port/lifecycle.c::exit_callback` L44–62](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/lifecycle.c#L44-L62) sets `closing=1`, waits **only for `card_lock`**, inspects/breaks GE and calls `sceKernelExitGame`. It does **not** wait for or explicitly flush a future binary recorder; a fast HOME exit can cut the export. `p4_card_io_begin()` L28–42 rejects new card operations after closing. Never piggyback on this card semaphore for a multi-tick export while sleeping: that can block real saves or make HOME wait; if sharing storage coordination, make it bounded, prioritize saves, acquire/release at a documented safe boundary and test close races in PPSSPP/Go.
- Frozen [`port/main.c::log_writer` L113–137](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/main.c#L113-L137) loops with **100ms sleep** and `p4_lifecycle_report();log_drain();`. Its thread is not a persistent independent crash daemon; it can be blocked on storage. If thread creation fails, `p4_log()` L311–312 instead drains **synchronously**, which may cause extra frame stalls. Do not make Diag-Lite per-frame probes depend on such fallback. Earlier [logger failure source proof](BASE_LOG_SAVE_BUILD_NEGATIVE_CONTRACTS_2026-11-20_QA06_WIP.md) shows baseline `log_drain` consumes queued bytes even after failed text log writes. New D1 ACK must be different.
- Frozen [`port/memcard.c` L146–189](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/memcard.c#L146-L189) demonstrates temp / `fflush` / `fclose` / `sceIoSync` / backup rename / `sceIoSync` guarded by the lifecycle card lock, **but it does not implement CRC reopen-readback and is NOT an already-proven generic incident writer**. Do not copy save code blindly, override its `.bak` or store incident files under `saves/card0` without explicit isolation.

## 4. 19:00 SEC-01p diagnostic identity correction changes what “last list” means

New scheduled source proof [`SEC01P_FREEZE_PROBE_BANK_IDENTITY_2026-11-20_WIP.md`](SEC01P_FREEZE_PROBE_BANK_IDENTITY_2026-11-20_WIP.md) confirmed directly against [frozen `rwsky.c` L1587–1647](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/29b0fcfdec70222a4052099b67fb4a11e8d8aff4/port/rwsky.c#L1587-L1647): in default `p4_pipeline=1`, the end-frame function caches submitted list in `pipe_last_list`, increments queue, toggles `pipe_set`, selects `list_store[next_bank]`, *then* handles L+R+SELECT freeze and prints `FREEZE frame ... list %x` referring to **next selected bank**, not known last submitted or displayed bank. This is misleading diagnostic evidence but **not proven memory corruption**. RESONANCE01 must log `submitted_bank/start/end/GE_id/seq`, `selected_next_bank`, and separately positive GE-finished and accepted-display bank/seq. Never label the next bank as a frozen in-flight GE buffer; do not synchronously read unfinished list contents on PSP.
