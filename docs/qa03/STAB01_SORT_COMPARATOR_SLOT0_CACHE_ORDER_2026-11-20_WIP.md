## A. NEW source condition: both qsort comparators use **slot 0**, not the list argument

- [`yListCompareByWeightedKeyDesc FUN_002E6630` `src/Yajima/y_list.c` L1680–1790](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1680-L1790): first takes `s16 leftIndex/rightIndex` from the sorter, then **hardcodes** `((KwlnTask*)D_00882F70[0])->work` as the records being compared. For kinds 1,5,6,10 it reads at `work+0xA4+0x30*index`; otherwise `work+0x14+0x30*index`. Critically it reads `metadata= iGpffffb3d4+2` and `metadata[14 * ((DatPersonaRecord*)left/right)->id]` **with no local ID/resource-extent guard before comparison**. Therefore a malformed 16-bit roster ID can be accessed **by qsort BEFORE any later `datPersonaCachedRecord` memcpy**, even if a fix guards only that copy. Note: actual metadata resource length and whether such ID is sorted remain unknown.
- [`yListCompareByKeyDesc FUN_002E6B20` L1863–1935](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1863-L1935) also **hardcodes slot 0**, but compares `DatPersonaRecord.level` only, so it **does not have the same metadata-by-ID read**. It may still select wrong source records if a nonzero list slot is sorted and slot0 differs.
- [`yListSlotSortWeighted FUN_002E68B0` L1790–1858](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1790-L1858) and [`yListSlotSortByKey FUN_002E6C90` L1941–2005](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1941-L2005) accept **`s8 list`**, take `D_00882F70[list]` and enumerate that list's `sortedIndices`; but then each calls **`qsort(...,yListCompareByWeightedKeyDesc/ByKeyDesc)`**, which reads **D_00882F70[0] regardless of input**. **Conditional contract:** if callers only sort list 0, behavior is consistent. If any caller sorts nonzero list while slot0 has different `kind`, count or indices, the comparison would reference wrong memory. **We have not established any nonzero callsite**: public GitHub source search currently returns definitions but not direct usages; some game code may be ASM/recompiled. Do not mark this a real bug without call trace/symbol crossref.
- **Additional conditional output-layout discrepancy:** both sorters rebuild destination at **`work+0x14+0x30*writeIndex` regardless `kind`**; the [`yListSlotEntry` accessor L830–851](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L830-L851) reads kind 1,5,6,10 records at **`work+0xA4+0x30*index`**. The gap is **0x90=144 bytes**, and sorted `id` is read from kind-dependent input. If sorting a kind6 list actually happens, reader and sorter destination layouts may conflict; but the intended sort might exclusively target other kinds. **Runtime callsite kind/list essential**, do not patch blindly, and don't infer a crashing sort from this arithmetic alone.

## B. NEW initialization-order discriminator: Register (kind 6) does not call all-persona cache seeding

- [`yListSlotRefresh FUN_002E4090` L670–753](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L670-L753): kind6 enumerates active roster and compares to cached Compendium without attempting to seed it; **kind8 explicitly calls `datPersonaInitAllRecords()` at L742 before enumerating IDs 1..191**. Therefore the cache state **can depend on which code path has executed before Register** if no other initialization occurs. Global init/callsite order is not established; **do not claim entering kind8 is necessary** or seed automatically in a fix.
