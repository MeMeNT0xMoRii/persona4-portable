## STAB-01 — Compendium nil-cache danger exists in more than one original path

Pinned original [src/Yajima/y_list.c L663–735](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L663-L735) case 6 of **yListSlotRefresh FUN_002E4090** copies a roster Persona record, checks its metadata arcana, then calls **memcpy(&registered, datPersonaCachedRecord(current.id), 0x30)** with **no explicit NULL guard**. In contrast, case 2 in the same function explicitly checks the cached pointer before copying: this suggests the unguarded case is relying on an invariant that may fail on unusual edited saves, but does not show a real crash in current P4P.

There is an **additional independent unguarded cached-record read** in [src/Yajima/y_list.c L1934–2005](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/Yajima/y_list.c#L1934-L2005): **yListSlotSortByKey FUN_002E6C90** sorts records, extracts their IDs, then zeroes destinations and copies 0x30 bytes from datPersonaCachedRecord(sortedIds[writeIndex]) **without checking for NULL**. This is not proved to execute in the user's exact Compendium Register route; map its active caller/list kind before patching. It may also affect independently sorted menus with particular cache states.

Original [src/g_data/g_data.c L2696–2713](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/g_data/g_data.c#L2696-L2713) **datPersonaCachedRecord FUN_0010FCB0** verifies ID in [0,255] and **returns NULL if the cached record's active flag is clear**. Thus a valid roster Persona ID does not imply that corresponding cache has been initialized.

**Critical non-obvious trap:** Original [src/g_data/g_data.c L2728–2777](https://github.com/Raikaru/Persona4-Decompilation/blob/363eab8a966d60a9773b45f330f2344329ec4f0a/src/g_data/g_data.c#L2728-L2777) **datPersonaResolveRecord FUN_0010FDE0** may **copy a missing Persona into the cache and still return NULL** on that invocation. Therefore **replacing datPersonaCachedRecord by datPersonaResolveRecord and immediately memcpy-ing its return is NOT a safe fix**. It may also change save/inventory semantics by mutating the global cache. Determine if a missing cache entry is an expected newly acquired Persona or a malformed save state before selecting a safe fail-closed behavior. Record origin ID, flag state, list kind, roster slot, return pointer and whether one task is refreshing/sorting; do not log confidential actual save content publicly.

**Proposed debug test:** Use COPIES of an original normal save, a minimal changed roster and a complex edited save; enter Compendium Register, Withdraw, Release and Sort; log exact first missing cache ID, cache active flag and origin (refresh vs sort). A source-level guard can preserve normal Vanilla flow, but any fallback that invents a cached record or silently drops entries needs semantic review and T2/T3 regression with save/reload. User's existing freeze cause remains T0.

## AUDIO-01 / VIDEO-01 — performance, I/O and movie→title boundary

Current [port/audio.c L1–75](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/audio.c#L1-L75) already has **one SAS audio worker and one separate loader thread**. Five static stereo VAG rings use **5 × 2 × 2048 × 16 = 327,680 bytes (320 KiB) main RAM**, plus two 32KiB thread stacks, not including index/bank buffers. Synthesis occurs with GRAIN=512 and Output2, not an ad-hoc full-game music decode on main-thread every frame.

[port/audio.c L250–332](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/audio.c#L250-L332) reads audio in 256-block chunks on the loader thread, refills via sceIoRead, writes back ring cache, pre-fills half a ring, sleeps 10ms when no more immediate work. [L482–515](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/audio.c#L482-L515): on **produced sample shortfall**, p4_audio_underruns increments, voices stop and channel closes rather than only losing one grain; a media-I/O spike can therefore become a visible **audio dropout**. This does NOT prove that audio is responsible for game FPS loss or scene stalls. Instrument audio loader CPU, underruns/errors, I/O latency alongside GE/CPU at field transitions, shops and music crossfades before removing/reducing audio quality.

[port/audio.c L669–699](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/audio.c#L669-L699) pauses with a **500ms acknowledgement timeout**, and video start [port/video_game.c L44–80](https://github.com/MeMeNT0xMoRii/persona4-portable/blob/dev/v0.27-perf06/port/video_game.c#L44-L80) drains GE, captures current display framebuffer, pauses/suspends SAS/codec, plays movie, restarts audio, **restores captured display buffer**, calls p4_video_renderer_end then returns to game. Restoring the old display buffer is **one conditional candidate** for the known title-return flash, but exact first 3 actual presented buffers and clears remain unmeasured. Do not change video/audio lifecycle solely because a black/white screen was observed; check GE wait, movie result, buffer identity, first 3 present boundaries, audible resume, 10 cold/warm title cycles. Preserve known-correct CRI logo centering.

**Combined acceptance**: do not trade game stability or audio for more FPS. Run native Go main-menu→movie→title, Junes→battle music/room, Velvet fusion audio and quick save/HOME while collecting frame pacing, ring underruns, GE completion and memory; test video failure cases separately. No source bug was corrected in this research.

## Why these three subsystems were researched together

The next actual build may change GE buffer size, source graphics pipeline, text geometry and optional fusion behavior. These changes can alter **heap headroom**, **Persona cache invariants**, **resource loading timing** and **movie/audio pause/restore** even when the visible change seems limited to rendering. Each should be included in the new-build regression suite and in the PPSSPP bot’s deterministic failure packet. No subsystem is considered fixed or performance-qualified merely because its source was mapped.
